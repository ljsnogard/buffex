# `known_bug_writer_busy_loops_on_spurious_wake_` 的定位与结案

日期：2026-10-01 02:25
涉及：`src/ring/tests_.rs`（主体）、`src/ring/half_.rs`、`src/ring/ring_core_.rs`

## 1. 现象

buffex 把 `abs_buff` 依赖升到 `de05cd7`（Demand 类型域收紧 + `DiffT`）后，
`known_bug_writer_busy_loops_on_spurious_wake_` 的两个运行时变体都失败，但**不是**文档
预期的「空转 → `Cancelled`」，而是：

```
panicked at src/ring/ring_core_.rs:252:
[Ring::try_read_internal_] take(0)
```

## 2. 定位：用例自身踩了 `Demand::less_than` 的语义变更

writer 用例的读端写的是：

```rust
let demand = Demand::less_than(1);   // 期望「最多 1 个」，实际是不等式 {0}
...
let demand = Demand::less_than(2);   // 期望「最多 2 个」，实际是 {0, 1}
```

`less_than` 的语义在 abs_buff 的 “Refactor Demand”（`898f5b3`，见
`abs_buff/dev-notes/demand-20260930-2154.md`）里被纠正过：

| abs_buff 版本 | `less_than(u)` 的取值集合 | `max()` |
|---|---|---|
| `be9d2b2` 及更早（名字骗人） | `{0, ..., u}` | `Some(u)` |
| `898f5b3` 起（严格小于） | `{0, ..., u - 1}` | `Some(u - 1)` |

于是 `less_than(1)` → `max() == Some(0)` → `take = min(max_len, ready) == 0` → 断言炸掉；
`less_than(2)` 只借出 1 格，后面对「取走 2 个」的断言同样过不了。这两个调用点属于
`ea52d6e`（Adapt abs_buff update on Demand）那一轮批量适配（`less_than(BUFF_SIZE)` →
`no_more_than(BUFF_SIZE)` 等）漏掉的部分。

## 3. 实现侧的两个「历史缺陷」的现状

1. **写者按 `data_size()` 判定空间**（`Producer::handle_event`）：当前实现已改为
   `Producer::wake` 按 `pos.free_size() < min_demand` 判定（`half_.rs`），文档里的
   `handle_event` 已不存在。即「提前唤醒」这一半**早已修好**，只是用例因为上面的
   `take(0)` 从未跑到那里。
2. **park future 中途 drop 不释放绑定**：仍然存在。`wake_slot_` 与 `opt_demand_` 只在
   poll 返回 `Ready` 时清理；在挂起状态下被 drop（取消 / `select` 落败）时不清理。后果：
   * 下一次 park 的首次 poll 把残留槽位误判成「已经注册过」→ 立即 `Ready(None)` →
     `ring_*_async` 循环在**一次 poll 内**同步空转（reader 侧用例描述的正是这个）；
   * 下一次 park 的 `init_demand_` 静默失败（残留旧 demand 继续生效），对端 `wake()` 按
     过时下限判定，并可能解引用已释放的 `Demand`（悬垂指针）。

## 4. 决策与实施

讨论后确定：

* 在既有未提交改动（`ring_core_.rs` / `tests_.rs` 的适配）之上继续，最后**一并提交**；
* 修 writer 用例的两处 `less_than` → `no_more_than`（与同一文件里既有的适配写法一致）；
* 两个 `known_bug_*` 用例**改名为普通回归用例**（缺陷已修或本次修掉）：
  `known_bug_reader_second_wait_busy_loops_` → `reader_can_park_again_after_cancelled_wait_`、
  `known_bug_writer_busy_loops_on_spurious_wake_` → `writer_woken_only_when_enough_free_space_`；
* 补齐 park 生命周期：`RingHalf_` 新增 `release_()`（清 `wake_slot_` + 释放
  `opt_demand_`），poll 的正常收尾、`ConsumerParkFuture` / `ProducerParkFuture` 的
  `Drop`、以及 `park_async` 返回的适配器（`ConsumerParkAsync` / `ProducerParkAsync`，
  它们在构造时就已经绑定 demand，只是还没转换成 future）的 `Drop` 都调用它。适配器为此
  改成持有 `Option<&mut ...>`，以便 `into_future` / `may_cancel_with` 用 `take` 移交借用
  而不是从实现了 `Drop` 的类型里移出字段。空转的验收仍由查询预算令牌（`BudgetToken`）
  把「空转」截断成有界失败。
* 顺带补齐同一轮适配漏掉的两处：`smoke_test_sync_` 的 `less_than(BUFF_SIZE)` →
  `no_more_than(BUFF_SIZE)`（与异步孪生用例一致），以及 `try_read_limits_count_by_max_`
  文档里仍写 `less_than` 的过时描述。

## 5. 验证

* `cargo test --lib`：**41 passed**（原 40 + 新增
  `ring::half_::tests_::dropped_park_future_releases_half_binding_`）；`cargo clippy
  --all-targets` 无告警。
* 变异校验（改回缺陷版本，均应被抓住）：
  * `Producer::wake` 用回 `data_size()` → writer 回归用例**挂死**（漏唤醒，预算令牌无法
    截断，用 timeout 截断）；
  * `release_()` 只 reset demand、不切 `wake_slot_` → 新单测失败；
  * `release_()` 只切 `wake_slot_`、不 reset demand → 新单测失败；
  * 适配器 `Drop` 改成 no-op → 新单测失败；
  * `ConsumerParkFuture` / `ProducerParkFuture` 的 `Drop` 改成 no-op → 新单测失败。
  变异均按字节还原（`cmp` 校验）。

## 6. 未决 / 遗留（本次未动）

* `wake_slot_: Option<Waker>` 是非原子字段，而 `Ring` 是 `Send + Sync`、两个半部可跨线程
  持有。对端 `wake()` 读这个槽位与持有者写它之间没有原子/内存序保护（`opt_demand_` 倒是
  原子的）。当前测试都跑在单线程运行时上，掩盖了这一点。若要真正跨线程，需要把唤醒槽位
  换成原子 waker（例如 `atomic_waker` 式的实现），并与 `opt_demand_` 的 init/reset 建立
  明确的内存序关系。
* 「漏唤醒」无法用取消令牌截断（park 之后再也不会被 poll），因此 writer 用例在回归时表现
  为挂死而不是失败；若希望 CI 里有界失败，需要给该用例加一个运行时无关的轮询预算/超时。
