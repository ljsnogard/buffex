# `channels` 模块的 API 外观设计

> 范围：`buffex` 新增的 `src/channels/` 模块（有界 SPSC / MPSC 两类队列）。
> 本文记录**设计意图、最终落地的 API 外观、以及关键取舍的因果链**。
>
> 日期：2026-09-24。基线提交：`7f8c762`（`dev/0.3.0`）。
> 改动前工作区状态：`buffex` 的 `Cargo.toml` 已有一行未提交改动（新增
> `abs_async_iter` 依赖），经确认后在此基础上继续。

---

## 0. 结论速览

1. **承载复用 `circ_buff`，不另造缓冲**：两类队列的消息就存放在
   `circular_buff` 的环形缓冲里；`channels` 只做「命名 + 抹平构建 + 补异步迭代
   形状」三件事。
2. **同步原语全部来自 `atomic_sync`**：多写者竞争用其**协作式读写锁**
   （`CooperativeRwLockOwned`）。本模块没有自造锁，也没有自造缓冲。
3. **两端复用同一个 `abs_async_iter::TrAsyncIterator`**，不另立 trait。写端的
   产出物是「一段可写空间」，读端的产出物是「一段可读数据」；两者都在 **drop 时
   提交**。
4. **`T` 不需要 `Copy`，也不需要 `Clone`**：段借出的是内存本身，调用者可以在
   缓冲区里**原地构造**消息（含带堆内存、不可平凡拷贝的类型），也可以就地借用。
5. **每端两类入口**：一次一个现成消息（`send` / `recv`），或批量 / 原地
   （`try_next` / `next_async` + 段）。
6. **「放弃写入」不引入空洞协议**：约定消息体自身表达「空」（`T = Option<U>`）；
   一次没构造任何单元就 drop 写段，等价于「什么也没发生」。

## 1. 设计意图（用户明确给出的约束）

1. 用上游 `atomic_sync` 新增的、**异步运行时无关**的协作式读写锁；
2. 用 `circ_buff` 作为队列的**承载**（消息容器），而不是重新发明一个；
3. 外观做成一个有界 SPSC 队列 + 一个有界 MPSC 队列，放在 `channels` mod 下；
4. **消费者端**与**生产者端**都要有「异步迭代」的形式，且**直接复用**
   `abs_async_iter::TrAsyncIterator`；
5. 多生产者之间**通过读写锁排队竞争一个写入位**；争取到之后即可写入，
   **后续排队者不必等前面的写完**才拿到写入位；
6. **不要给 `T` 加 `Copy` 约束**——`circ_buff` 本身就不需要，而且它借出内存段的
   能力正是「原地构造消息本体」的关键；
7. 生产端提供两类 API：一类一次只放一个、消息本体现成（不暴露段）；另一类一次
   连续放多个、消息本体可能不可 `Clone`（提供段的薄封装让发送者自己填）；
8. 「消息空洞」暂不处理：大不了让消息体本身是 `Option<T>`，没及时写入就是
   `None`。

## 2. 最终落地的公开 API

```
buffex::channels
├── ChannelError                     // 两类队列共享的错误类型
├── SpscChannel                      // ::with_capacity(n) -> Self
│   └── .into_parts::<T, A>().await  // -> (SpscSender, SpscReceiver)
│       ├── SpscSender               // 实现 TrAsyncIterator<Item = SpscWriteSegm>
│       │     ├── send(T)                      // 一次一个（消息现成）
│       │     ├── try_next(&Demand)            // 非阻塞：借出一段可写空间
│       │     └── next_async()                 // 异步对偶（队满时真的 park）
│       └── SpscReceiver             // 实现 TrAsyncIterator<Item = SpscReadSegm>
│             ├── recv() -> Option<T>          // 一次一个（值 move 出来）
│             ├── try_next(&Demand)            // 非阻塞：借出一段可读数据
│             └── next_async()
└── MpscChannel<T, const S: usize>   // S = 写者数量上界
    └── .into_parts().await          // -> (MpscSender, MpscReceiver)
        ├── MpscSender               // Clone：每个克隆体是一个独立写者
        └── MpscReceiver
```

段类型（`SpscWriteSegm` / `SpscReadSegm` / `MpscWriteSegm` / `MpscReadSegm`）
就是 `circ_buff` 的 `ReclSliceMut` / `ReclSliceRef` 的类型别名，因此调用者拿到
的是 `abs_buff` 的段接口（`least_count` / `iter_slices(_mut)` /
`move_items_*`），不是本模块另造的一套。

### 2.1 两端的产出物与提交时机

| 端 | 产出物 | drop 时提交 |
| --- | --- | --- |
| 写端 | `ReclSliceMut`（一段逻辑连续的可写空间） | 「已构造的单元数」→ `advance_write` |
| 读端 | `ReclSliceRef`（一段逻辑连续的可读数据） | 「已消费量」→ `advance_read` |

「drop 即提交」是 `circ_buff` 段类型固有的语义（`WriterReclaim` /
`ReaderReclaim`），本模块只是把它暴露出来。**由此推论：写段必须在读取之前
drop**——这是一条使用约束，测试里专门有一条断言把它钉住。

### 2.2 `Ok(None)` 与 `Err(Closing)` 的分工

沿用 `abs_async_iter` 的约定，两端一致：

* `Ok(None)`——**暂态**没有产出：写端「没空位 / 写入位被占」，读端「暂无数据」。
  调用者可稍后重试；
* `Err(Closing)`——**终止**：写端已关闭且已读空（EOF），或读端已关闭。

`next_async` 在暂态情形下**真的 park**（挂在底层的 `write_async` /
`read_async` 等待 future 上，由对端提交唤醒），而不是空转或立即返回
`Ok(None)`。`try_next` 才是非阻塞的那一个。测试
`spsc_send_next_async_parks_until_space_` 手动轮询两次把它钉住：第一次
`Pending`、读端腾出空间后第二次 `Ready(Ok(Some(_)))`。

## 3. 关键决策与因果链

### 3.1 写端为什么也必须实现 `TrAsyncIterator`

`TrAsyncIterator` 的约定是 `Result<Option<Item>, Err>`。写端的 `Item` 是
「一段可写空间」，`Ok(None)` 天然对应「这次拿不到写位 / 没空位」——**语义完全
吻合**，因此不需要另立一个 yielder trait。

> 早期草案曾经定义过 `TrAsyncYielder`（把 `MayCancelOutput` 收紧为
> `Result<Item, Err>`，理由写端没有「正常结束」的中性态）。那个理由站不住：
> 写端确实有中性态——「本轮没空位」，它与终止态 `Err(Closing)` 是两回事。
> 该草案已删除。

### 3.2 产出物为什么能是 `'static` 的段

`TrAsyncIterator::Item` 是**无生命周期参数**的关联类型，而段必然借用核心。因此
产出物需要「脱离 `next_async` 的借用存活」，做法是：

* 把段的生命周期延长为 `'static`（`extend_write_segm_` / `extend_read_segm_`，
  只有 `transmute`、不改位模式）；
* 与此同时，**核心由端半部持有的 `Shared` 句柄保活**——`Producer` /
  `Consumer` 内部就是 `Shared<CircCore>`，MPSC 另在 `MpscShared::core_ref_`
  显式持一份。

这是本模块唯一的 `unsafe`，安全论证写在两个 `extend_*` 函数的文档里
（AGENTS.md §7）。

### 3.3 MPSC 的写者共享：为什么是 `UnsafeCell` + 写锁

`Producer::try_write` 需要 `&mut self`，而：

* `mm_ptr::Shared` 只提供 `Deref`，**没有** `DerefMut`；
* 多写者又必须共享同一个 `Producer`（它的 `core_ref_` 就是那块唯一的环形缓冲）。

因此 `MpscShared::producer_` 用 `UnsafeCell<Producer<..>>`，访问统一走
`produce_()`，其安全前提是「**调用者必须持有 `write_queue_` 的写许可**」。
写者之间的互斥正是由那把协作式读写锁承担，所以 `&mut` 的独占性成立。这是本模块
第二处、也是最后一处 `unsafe`。

### 3.4 写入位的持有范围与「后续排队者不必等写完」

* 锁只覆盖「取得写入位」这一段临界区，**不含数据搬运**：`try_next` 在返回段之前
  就释放锁；
* 但**段的 Drop（提交）仍会推进写位置**，所以「取位」这一步事实上必须独占——
  否则两个写者会拿到同一个 `wp` 而互相覆盖；
* 结论：写者 A 取到位后释放锁 → 写者 B 可以立刻排队取下一个位；A、B 的**构造
  过程**不互相阻塞。这就是需求 5 的落点。

### 3.5 `send` / `recv` 与段路径的关系

* `send(item)`：内部就是 `try_write(&exactly(1))` + 在段里原地构造 1 格 + drop
  提交。它**不暴露段**，适合「消息已经现成」的场合；
* `try_next(&demand)`：把段直接交给调用者，适合「批量、或消息不可 `Clone`、或
  要就地借用」的场合。

两者共用同一条底层路径，没有第二套实现。

## 4. 「放弃写入」的处理：约定消息体表达「空」

写者可能在**取得写入位之后**放弃（future 被取消、任务 panic、调用者显式放弃）。
本实现**不引入**「提交游标 + 每笔占位状态」的空洞协议，而是约定：

* 写者要么把消息构造完整；
* 要么把该槽位留成 `T = Option<U>` 的 `None`，由消费端按业务语义跳过；
* 一次没构造任何单元就 drop 写段 ⇒ 提交量为 0 ⇒ 写位置不前进，等价于
  「什么也没发生」。

这样就不必为 `circ_buff` 的核心增加「已占位、未提交」的第二个游标，也不必定义
主动设备端在该区间上的行为。代价是「放弃」在协议层不可区分于「本轮没写」，需要
业务自己用 `Option` 表达——这正是需求 8 认可的方向。

## 5. 已验证记录

```
cargo check --all-targets     # 无 error / warning
cargo clippy --all-targets    # 零告警
cargo test --lib              # 59 passed; 0 failed; 2 ignored
                              # （其中 channels 13 个）
cargo test --doc              # 3 passed; 0 failed; 2 ignored
```

`channels` 的 13 个测试（均带中文文档注释，标注测试目标 / 手段 / 判定）：

**SPSC**

1. `spsc_fifo_roundtrip_`——构建 → `send` → `recv` 的 FIFO 闭环；
2. `spsc_is_bounded_`——容量满时 `send` 报 `Stuffed`，且不挤掉已有数据；
3. `spsc_close_then_eof_`——关闭后残留可读，读空后 `Closing`；
4. `spsc_rejects_zero_capacity_`——容量 0 在构造期被拒；
5. `spsc_in_place_constructs_non_copy_messages_`——**用 `String` 证明不需要
   `Copy` / `Clone`**：写段原地搬入 2 条、读段全部 move 出；
6. `spsc_both_ends_implement_async_iter_`——两端同一个 `TrAsyncIterator`，
   含写段产出与 EOF；
7. `spsc_full_try_next_yields_none_`——非阻塞入口在队满时给暂态 `Ok(None)`；
8. `spsc_send_next_async_parks_until_space_`——`next_async` 真的 park 并被
   读端唤醒（手动两次轮询）。

**MPSC**

9. `mpsc_two_senders_share_one_buffer_`——多写者共享同一块承载；
10. `mpsc_rejects_zero_senders_`——写者数为 0 在构造期被拒；
11. `mpsc_both_ends_implement_async_iter_`——两端迭代 + EOF；
12. `mpsc_in_place_constructs_non_copy_messages_`——`String` 批路径；
13. `mpsc_full_try_next_yields_none_`——队满时暂态 `Ok(None)`。

**新增**

* `src/channels/mod.rs`——模块门面与公开导出；
* `src/channels/error_.rs`——`ChannelError` 及从 `circ_buff` 错误的收敛映射；
* `src/channels/spsc_.rs`——SPSC 队列（薄包装 + 两端 `TrAsyncIterator`）；

* `src/channels/tests_/`——单元测试。

**修改（均为 crate 内部，不是公开 API 变更）**

* `src/lib.rs`——新增 `pub mod channels;`、`extern crate alloc;`、
  `x_deps::abs_async_iter`；
* `src/circular_buff/mod.rs`——`abs_comp_` / `core_` / `reclaim_` 提升为
  `pub(crate)`（`channels` 需要指名段的提交器类型与端契约 trait；对外仍不可达）；
* `src/circular_buff/spsc_.rs`——新增 `pub(crate) fn core_ref_of_()`，让
  `channels` 在不借用半部的前提下取得核心句柄（MPSC 的段保活需要）；
* `src/circular_buff/core_.rs`——`capacity()` / `free_size()` 由 `pub(super)`
  放宽到 `pub(crate)`（同上，仍不对外）；
* `Cargo.toml`——`abs_async_iter` 依赖（改动前已在工作区）。

**未修改**：`circular_buff` 的公开 API、任何行为、任何既有测试。
