# 消息协议载体 与 精细化生产端：设计讨论与可行性考察

> 范围：`buffex` 的 `src/channels/`（有界 SPSC / MPSC 队列）。本文对应两项待决设计：
>
> 1. **内部消息协议载体**：用一个不对外公开的枚举承载「用户载荷」与「给接收端的
>    提示」（发送端已关闭 / 本槽无效 / 正常荷载…），让接收端可以**有选择地**提醒
>    用户，而不把消息空洞暴露给最终用户；
> 2. **精细化生产端**：不再给 `Producer` 包一层锁容器，直接用 `CoopRwLock` 保护
>    它；更好地封装 `SegmMut`——一次性申请尽可能大的写段，再拆成细段分发给生产者，
>    **分段提交**。
>
> 本文是**讨论与可行性考察**，结论部分需要人类决策后才实施（AGENTS.md §1）。
>
> 日期：2026-09-24。基线提交：`0e7a300`（`Add experimental channel implement`）。
> 同期的 API 适配记录见 `channels-20260924-1230.md`。

---

## 0. 结论速览

1. **上游 trait 变更已适配**：`TrAsyncIterator::NextAsync` 的 `Ok` 侧不再包
   `Option`，因此两端 `next_async` 变成「要么产出、要么以错误终止」；「队满 / 暂无
   数据」这类**暂态**不再有返回值可表达，改为在 `next_async` 内部 `await` 底层的
   等待 future。非阻塞探询保留在 inherent 的 `try_next`。（已完成）
2. **发现并复现一处结构性缺陷**：MPSC 的写锁在**返回写段之前**就释放，而写位置
   要等段 drop 才推进 ⇒ 两位写者会拿到**同一个写位置**。实测两段首地址完全相同。
   这不是风格问题，是会导致读端读到未初始化数据的安全问题。（已用 `#[ignore]`
   测试钉住，修复方案待定）
3. **该缺陷与「精细化生产端」是同一个问题**：只要核心只有**一个**游标（`wp`，
   且只在提交时推进），那么「锁只覆盖取位」就不可能成立——除非引入
   **占位游标 + 提交游标**，以及**每槽位的状态**。
4. **协议载体正是「每槽位状态」的载体**：它既是需求 1 的答案，也是需求 2 得以成立
   的前提。两者应当一起设计。
5. **一个必须正视的代价**：把协议枚举**内联**进环形缓冲的每个槽位，会破坏
   `&mut [MaybeUninit<T>]` 这种**连续载荷切片**能力（`circ_buff` 现有的零拷贝批量
   路径依赖它）。有两条规避路线，见 §3.3。

## 1. 上游 trait 变更带来的语义收缩（已完成适配）

新的约定：

```rust
type NextAsync<'f>: TrMayCancel<'f, MayCancelOutput = Result<Self::Item, Self::Err>>;
```

于是 「本轮没有产出」**不再有类型位置**。原先用 `Ok(None)` 表达的两种暂态必须另找
归宿：

| 原语义 | 新归宿 |
| --- | --- |
| 写端：队满 / 写入位被占（背压） | `next_async` 内部 `await` 等待 future，不返回 |
| 读端：暂无数据 | 同上 |
| 读端：EOF / 已关闭 | `Err(ChannelError::Closing)`——恰好对应 trait 里 `Err` 表示「迭代结束」 |
| 非阻塞探询 | 保留在 inherent 的 `try_next`（不受 trait 约束，仍是 `Result<Option<_>, _>`） |

这与上游给 `Iterator` 的 blanket impl 完全一致：`Iterator` 耗尽时返回
`Err(IterEndedError)`，即 **`Err` = 迭代结束**，而不是「出错」。因此两端把
「关闭 / EOF」映射为 `Err(Closing)` 是符合约定的。

**副作用（正向）**：`next_async` 现在**保证**要么给出东西、要么终止，调用者不再需要
处理「成功但什么都没有」的分支。

## 2. 已复现的结构性缺陷：MPSC 写入位重叠

### 2.1 现象

```text
写者 A: [取位: wp=0 → 段A(offset 0)]  ······ 尚未提交 ······
写者 B:                              [取位: wp 仍是 0 → 段B(offset 0)]
```

`MpscSender::try_next` 的顺序是：

1. 取得 `CoopRwLock` 的**写许可**；
2. 调 `Producer::try_write(demand)` 借出坐标（**不推进 `wp`**）；
3. **释放写许可**，把段返回给调用者；
4. 调用者写入；段 drop 时才 `advance_write(k)`。

第 3 步是问题所在：`wp` 直到第 4 步才动，所以第 1 步的互斥**保护不了「写入位」**，
它只保护了「读一次 `wp`」。

### 2.2 实测

测试 `channels::tests_::mpsc_::mpsc_reservations_must_not_overlap_`：

```text
两位写者取得写入位后都未提交时，写入位必须互不重叠
  left: 0x55b79f3d49d0
 right: 0x55b79f3d49d0
```

两段可写空间的**首地址完全相同**。后果有两层：

* 直接后果：两位写者互相覆盖（丢消息）；
* 更严重：若 A 先 drop（提交 1 格，`wp→1`）而 B 的字节还没写完，读端在 `wp=1` 的
  范围内读到的是 B 尚未初始化的槽位——**读未初始化内存**。

该测试已加 `#[ignore]` 并在 `mpsc_` 模块头部标注缺陷；修复方案见 §3.4。

### 2.3 为什么这不是「实现疏忽」而是结构问题

`circ_buff` 的核心只有**一个**位置游标 `wp`，且它**在提交时**前进：

* 「借出坐标」与「推进位置」是分开的两件事；
* 中间这段时间里，被借出的区域对其它写者**不可见**，因此无法互斥；
* 换句话说：**核心没有「已占位、未提交」这个概念**，任何想「早点把锁放掉」的设计
  都会踩到这里。

这正是需求 2（精细化生产端）要解决的问题的另一面。

## 3. 设计讨论

### 3.1 协议载体：形态

不对外公开的枚举（草案）：

```rust
/// 环形缓冲里每个单元承载的**完整消息**：用户载荷 + 给接收端的提示。
///
/// 不对外公开：公开 API 只呈现用户载荷 `T`。
pub(super) enum SlotMsg<T> {
    /// 本槽无效（写者取得写入位后放弃，或租约过期被回收）。
    Void,
    /// 发送端已关闭：接收端读到它即知 EOF（**在带内**，因此顺序精确）。
    TxClosed,
    /// 正常荷载。
    Payload(T),
}
```

接收端的处理规则（默认路径）：

| 槽位 | `recv` / `next_async` | 说明 |
| --- | --- | --- |
| `Payload(t)` | 产出 `t` | 正常 |
| `Void` | **静默跳过**，并可计入计数 | 「不把空洞暴露给最终用户」 |
| `TxClosed` | `Err(ChannelError::Closing)` | 迭代结束 |

「有选择地提醒」通过**计数/观察入口**实现（不暴露枚举），例如
`Receiver::voids_skipped() -> usize`，或一个显式的
`try_recv_notice() -> Result<Option<Notice>, _>`。具体形态待定，但原则是
**默认隐藏、可选观察**。

### 3.2 协议载体的真正价值：它让「占位」变得可表达

单看需求 1，`Void` 似乎是可有可无的（当前实现里放弃写入 ⇒ 提交量为 0 ⇒ 根本没有
空洞，见 §2.3 的反面）。`Void` 真正的用武之地是**一旦「占位即推进 `wp`」**：

* 占位时把槽位初始化为 `Void`（或 `Reserved`）；
* 写者填入 ⇒ `Payload`；
* 写者放弃 ⇒ 保持 `Void`；
* 读端跳过 `Void` ⇒ **流不会因为一次放弃而永久卡住**。

也就是说：**协议载体是精细化生产端的前提**，而不是两个独立需求。

### 3.3 关键代价：内联协议 vs 连续载荷切片

把 `SlotMsg<T>` 作为环形缓冲的单元类型，会**丢掉** `&mut [MaybeUninit<T>]`：

* `[SlotMsg<T>]` 与 `[MaybeUninit<T>]` 布局不同——前者每格带判别式/填充，**步长
  不再是 `size_of::<T>()`**，无法用一段连续切片表示「N 个待构造的载荷」；
* 这会影响 `circ_buff` 现有的零拷贝批量路径
  （`move_items_from_input_async` / `move_items_to_output_async`，
  以及将来「一次 `read(2)` 灌满多个槽位」的用法）。

三条规避路线：

| 路线 | 做法 | 保留连续切片 | 代价 |
| --- | --- | --- | --- |
| **A. 内联枚举** | 缓冲单元 = `SlotMsg<T>` | ✗ | 最简单、最省内存；失去批量切片 |
| **B. 状态并行环** | 载荷仍是 `[MaybeUninit<T>]`，另开一个 `[SlotState]`（同容量） | ✓ | 两份缓冲、两套游标要同步；`circ_buff` 只承载其中一份 |
| **C. 槽结构体** | 单元 = `struct Slot<T> { tag: AtomicU8, payload: MaybeUninit<T> }` | ✗（但可逐槽借出 `&mut MaybeUninit<T>`） | 每槽可原子定态（§3.4 需要它）；仍需逐槽而非批量 |

**路线 C 是唯一同时满足「读端与写端并发安全」的**：只有当每格状态是**原子**的、
写入载荷后用 `Release` 置位 `Payload`、读端以 `Acquire` 观察，才谈得上「写者在读端
可能正在读的时候继续填」。若状态不是原子的（路线 A），「占位时先写 `Void`、稍后覆盖
成 `Payload`」就会与读端的读构成**数据竞争**（Rust 内存模型下的 UB）。

### 3.4 精细化生产端：可行性与所需的核心改动

需求：`CoopRwLock` 保护 `Producer`；一次申请**尽可能大的写段**，再拆成**细段**分发给
生产者；**分段提交**。

逐条考察：

**(1) 「直接用 `CoopRwLock` 保护 `Producer`」——可以，但**保护范围**是关键。**
`Producer::try_write` 需要 `&mut self`，所以共享 `Producer` 必然要内部可变性（当前
用 `UnsafeCell` + 写锁，见 §2）。这没问题；问题是锁的**作用域**：只覆盖「取位」在
单游标核心下**不安全**（§2 已实测）。

**(2) 「一次性申请大段、拆成细段」——目前不可表达。**
`ReclSliceMut` 的提交是**整体一次性**的：`as_segm_mut()` 产生的子段 drop 时只是把
消费量**累计**到父段的 `offset_`，真正的 `advance_write` 只在**父段 drop** 时发生。
所以：

* 子段可以独立「被填」，但**不能独立「提交」**；
* 想让细段各自提交，只能让每个细段各自持有 `WriterReclaim` 并调用
  `reclaim(n)` → `advance_write(n)`——而这就落回**单游标 + 乱序提交**的不安全问题。

**(3) 「分段提交」在单游标下的唯一安全形态：提交顺序 == 占位顺序。**
即细段必须按 FIFO 顺序 finalize；任一细段「占着位不提交」都会阻塞其后所有提交，最终
阻塞消费者（饥饿）。需要一条「租约超时 / 显式放弃 ⇒ 由后续写者代提交跳过」的回收
规则——而「代提交一个空洞」正是 `SlotMsg::Void`。

**(4) 双游标方案（推荐的长期方向）。**
给核心加第二游标，语义分工：

```text
rp ────────────► commit_wp ────────────► wp
   已消费            已 finalize（读端可见）      已占位（可能仍在写）
```

* **占位**（写锁内）：把整段每格置 `Reserved`，然后 `wp += n`；释放锁；
* **写入**（写者自行进行）：填 payload → `state.store(Payload, Release)`；
* **放弃 / 超时**：`state.store(Void, Release)`；
* **提交游标推进**：只沿**连续已定态**区间前进（`Payload` 或 `Void` 都算定态，
  `Reserved` 不算）；
* **读端**：只在 `rp .. commit_wp` 内取数；`Payload` 产出、`Void` 跳过。

这样「锁只覆盖取位」「细段独立提交」「空洞不暴露给用户」三者同时成立。

**(5) 双游标带来的连带影响（必须一并设计）。**

* `data_size()` 的含义要从 `rp..wp` 改成 `rp..commit_wp`；
* `advance_write` 需要拆成「占位推进」与「finalize 推进」两个入口；
* **主动设备端**（`DevProducer` / `DevConsumer`）必须定义在 `Reserved` 区间上的
  行为——泵不能越过未 finalize 的区域搬运；
* 关闭 / EOF 语义要重新表述（`TxClosed` 作为带内哨兵，恰好解决多写者场景下
  「关闭」与「残留数据」的顺序问题）；
* 容量为 `MAX_CAPACITY` 时，`wp`/`commit_wp`/`rp` 三个游标都要放进状态字，位宽需要
  重新核算。

### 3.5 短期可落地的修法（不改核心）

在双游标落地之前，MPSC 要**先恢复正确性**，代价是写者串行：

* **闭包式入口**：`MpscSender::with_write_segm(demand, |segm| ...)`，锁覆盖
  「取位 → 闭包执行 → 提交」全程。调用者仍能零拷贝就地构造；写者之间串行。
* 或者把**写许可放进返回的写段**（写段借用发送端并持有 `WriterGuard`）。这需要
  自行处理「会话 + 守卫」的自引用（`Box` 固定地址 + 受控 `unsafe`），复杂度高于
  闭包式，但能保住「段可以脱离一次调用存活」的用法。

两者都属于**公开 API 变更**，需人类确认后实施。

## 4. 建议的推进顺序

1. **先修安全**（§3.5 二选一）：让 MPSC 的写入口在提交前一直持有写锁。这一步不改
   核心，风险最低，且能立刻解除 §2 的缺陷。
2. **再定协议载体形态**（§3.1 + §3.3 路线 A/B/C）。若接受失去连续载荷切片，路线 A
   最简；若要保留，路线 B；若要为下一步铺路，路线 C。
3. **最后做双游标核心扩展**（§3.4），在这一步把「短锁 + 细段 + 分段提交」一次做对，
   并同步定义主动设备端在 `Reserved` 区间上的行为。

不建议跳过第 1 步直接做第 3 步：中间态会让缺陷长期留在主干上。

## 6. 追加评估：单体槽 + bulk 预告头 + 空洞丢弃（含一轮修正）

> 协议草案（用户提出）：
>
> * **单体消息**：直接占 **1 个槽**把载荷带出，不额外占槽；
> * **bulk 写**（申请连续 > 1 格）：在连续段**开头预插一个「预告头」**，内含连续段
>   长度；并**预插内存空洞**。写完后消费者可完整收到 bulk；即使没写完，也能拿到
>   **先写好的部分**；
> * **消费端规则**：先 read，读到空洞就**直接丢弃、视作已读**，继续等下一条；空洞
>   对上层不可见。

### 6.1 修正：预填充让消费端**没有**在飞状态

本节初稿曾断言「必须让消费端区分 `Reserved`（在飞）与 `Hole`（已废弃）」，并进一步
要求「每槽位状态必须原子可观察」。**这两条在补充了下述前提后都不成立，予以撤回。**

前提（即用户澄清的机制）：**Sender 在预留阶段就把整段用「空洞值」预填充**，但
**不真正提交**——`wp` 仍然只在**段 drop（提交）**时推进。于是：

| 区间 | 归属 | 内容 |
| --- | --- | --- |
| `[rp, wp)` | 消费端可读 | 每格**必然已初始化**（空洞或载荷），且**不会再被写** |
| `[wp, reserve_wp)` | 生产端在飞 | 已被预留并预填充，消费端**看不到** |

由此：

* **消费端不需要 `Reserved` 状态**。它看到的只可能是「空洞」或「载荷」（bulk 帧内同理），
  因此「读到空洞 ⇒ 丢弃、视作已读、等下一条」是**安全且完备**的；
* **不需要每槽原子状态字**。生产端写的是 `[wp, reserve_wp)`，消费端读的是 `[rp, wp)`，
  **两者槽位区间不相交**，不存在同一格的并发读写；
* **不需要新的「只唤醒不推进」原语**。提交走既有 `advance_write(n)`，它本来就会
  `fire_consumer`（`advance_write(0)` 等价于「只唤醒」）。

**预填充的真正作用**：让「**提交整段**」变得安全。因为整段每一格都已初始化，所以
即使生产者只写了 `k < n` 格，也可以按整段长度提交——未写的格成为空洞，消费端照规则
丢弃。这正是「部分填充的 bulk 仍能交付已写前缀」得以成立的前提，而**不必**让消费端
感知任何在飞状态。

### 6.2 仍然需要的东西

**(1) 跨写者的提交顺序（唯一真正的硬约束）。**
预填充只让乱序提交从「UB」降级为「**内存安全但会丢数据**」：

```text
A 预留 [0,3)（已预填充空洞），B 预留 [3,6)
B 先提交  →  wp = 6
消费端读 [0,3)：全是空洞 → 丢弃 → rp = 3
A 随后才写入载荷 —— 槽位已被 rp 越过，数据永远读不到
```

所以生产端仍须二选一：

* **(a) 锁覆盖「预留 → 提交」全程**：写者串行，正确，最简单，不改核心；
* **(b) 生产端内部「预留游标 + 提交游标」**：预留游标（`reserve_wp`）让写者互不重叠；
  提交游标只沿**连续已提交前缀**推进，而它**就是消费端看到的 `wp`**。

**(b) 的全部簿记都在生产端内部**——消费端只读 `wp`，不新增任何状态、不新增任何
可见语义。这正是「不把生产端的竞争状态扩大影响到消费端」。

**(2) bulk 帧由多个生产者分摊时，谁负责定局。**
「一次预留大段、拆细段分发」与「一帧一个预告头」仍有张力：单格生产者代表不了整帧。
两条路：各细段自行定局（整帧定局 = 无未定局成员）；或一个原子计数把未定局细段数减到 0
的那个负责定局 + 唤醒。需拍板。

**(3) `BulkHead(n)` 的 `n` 是预留长度，足够了。**
消费端按 `n` 读完成员、丢弃其中的空洞即可，**不需要**「实际长度」字段；因此初稿
「头里给实际长度 ⇒ 需定局回填」的顾虑不成立。

**(4) 容量与 `Demand` 要按实际占用算。**
`n` 个成员 + 1 个预告头 = `n + 1` 格（单体消息则 1 格）。`free_size`、容量校验、背压
都要用实际占用。

**(5) 「空洞值」的类型。**
推荐用协议枚举的默认变体（`SlotMsg::Void`）——它是**协议类型**的默认值，因此 `T`
**不需要** `Default` 约束。若空洞值字面上取 `T::default()`，`Default` 就会成为队列的
公开 API 约束，代价明显更大。

**(6) 预填充的开销与 drop。**
* 预留 `n` 格 = 写 `n` 次空洞值（可逐格 `move_items_from_buff`，顺便把提交量置为 `n`），
  生产者再写 `k` 格——每格最多两次写，需记账但可接受；
* 环形回绕后，同一格可能遗留上一轮的 `Payload`；预填充必须用**赋值**（`*slot = Void`）
  而非裸写，才能触发旧值 drop。

### 6.3 判定（修正后）

| 问题 | 回答 |
| --- | --- |
| 方向 | **对**；预告头 + 空洞是「部分写入仍交付前缀」的标准解法 |
| 消费端 | **干净**：只需「空洞丢弃、载荷交付、bulk 按头长度收帧」。无在飞状态、无需原子状态字、无需新唤醒原语 |
| 生产端 | 仍需「预留游标 + 提交游标」的簿记（或锁覆盖全程）；**全部在生产端内部**，不外溢到消费端 |
| 够不够完整 | 补齐 (1)(2) 后即完整；(3)(4)(5)(6) 是实施细节 |
| 可实现吗 | **可实现**。核心改动 = 状态字容纳第三个游标（`reserve_wp`）+ `channels` 侧的预留/提交流水；**消费端语义不变** |
| 与既有工作的关系 | (1) 与 §2 已复现的写入位重叠、§3.4 的双游标是**同一套改动**，应合并推进 |

## 7. 追加修正：bulk 帧独属单个生产者；放弃大段预留

> 补充澄清：
>
> * **bulk 帧不可能有多个生产者**——它独属于**申请该写段的那一个**生产者；
> * **放弃「大段预先申请」**：写者需要多少就给多少。

### 7.1 被取消的两件事

| 原议题 | 现状 |
| --- | --- |
| §6.2(2)「bulk 帧由多个生产者分摊时谁负责定局」 | **议题不存在**：一帧一主，定局责任天然明确（就是申请它的那个生产者） |
| §3.4「一次申请大段 → 拆细段分发 → 分段提交」 | **放弃**：不再有大段预留，也就没有细段、没有跨细段的提交顺序问题 |

连带消失的复杂度：

* 不需要「细段未定局计数」这类跨生产者同步；
* **一次预留 = 一次提交**，提交单位与预留单位一一对应，预留记录表因此很简单
  （每条记录 = 一个在飞写者的 `(start, len)`；在飞数量 ≤ 容量）；
* 预留长度在申请时就已知，`BulkHead(n)` 的 `n` 在**预留时**即可确定，不需要回填。

### 7.2 「写者需要多少就给多少」对 API 的含义

预留量 = 申请量（精确值），而不是「有多少给多少」。于是：

* `Demand` 的用法从「`at_least` / 上限」收敛为**精确数量**：写者声明 `n`，暂时不足
  `n` 即 `Stuffed`（或异步等待），不做部分授予；
* `n = 1` ⇒ 单体消息，**无预告头**，1 格即 1 条消息；
* `n > 1` ⇒ bulk，段首放 `BulkHead`，其后 `n` 个成员格（或 `n-1` 个成员 + 1 个头，
  见 §7.3），成员未填即空洞。

### 7.3 唯一剩下的细节点：预告头是否额外占格

两种口径，需择一（影响容量与 `Demand` 语义）：

| 口径 | 预留格数 | 写者可用成员数 | 说明 |
| --- | --- | --- | --- |
| A. 头在段内 | `n` | `n - 1` | 「申请 `n` 格」与实际可写条数差 1，调用者要自己减 |
| B. 头额外占格 | `n + 1` | `n` | `Demand` 语义保持「我要 `n` 条消息」，实现内部多占 1 格 |

倾向 **B**：`Demand` 的语义只关于**用户消息条数**，协议开销（头）由实现内部吸收并计入
容量校验，调用者不必关心。

### 7.4 修正后：唯一真正的待决项回到「锁的作用域」

放弃大段预留之后，仍然存在一条硬约束（§6.2(1)）：**跨写者的提交顺序**。而它现在
等价于「写锁到底覆盖多大范围」这个二选一：

| 方案 | 锁范围 | 是否需要核心加游标 | 写者是否互相等待 |
| --- | --- | --- | --- |
| **(a) 锁覆盖全程** | 取位 → 写入 → 提交 | **不需要**，现有单游标 `wp` 即可 | 是（后到者等前面写完） |
| **(b) 锁只覆盖取位** | 取位 | **需要** `reserve_wp` + 提交游标 | 否（这就是最初的需求 5） |

**(b) 的必然性推导**（三条要求互相锁定）：

1. 「消费端不得出现在飞状态」⇒ `wp` 只能在**提交**时推进；
2. 「锁只覆盖取位」⇒ 后续写者必须能拿到**互不重叠**的位置 ⇒ 需要另一条在**预留**时
   推进的游标 `reserve_wp`；
3. 「提交可能乱序」⇒ `wp` 只能沿**连续已提交前缀**推进 ⇒ 需要每条预留的提交状态。

三条合起来 = **生产端内部的「预留游标 + 提交游标 + 每条预留的提交状态」**，而
消费端只读 `wp`，语义与现在完全一致。

因此 (a)/(b) 的选择不是「要不要复杂度」，而是「**要不要保留最初那条需求**
（后续排队者不必等前面写完）」。若保留 ⇒ 必须做 (b)；若不保留 ⇒ (a) 即刻可落地，
且不需要任何核心改动。

## 8. 决策落地（本轮实施）

两项决策：

* **预告头额外占格**（口径 B）：`n` 的语义始终是「用户消息条数」，协议开销由实现内部
  吸收并计入容量；
* **锁覆盖全程**（方案 a）：放弃「取到写入位置就放锁、后续排队者不必等前面写完」这一
  优化；写者串行，先以最简单的方式拿到正确性。

### 8.1 实际实现

**内部槽位协议**（`src/channels/slot_.rs`，`pub(super)`，不外露）：

```rust
pub(super) enum SlotMsg<T> {
    Void,                      // 空洞（内部协议的 Default）
    Payload(T),                // 单体消息，或 bulk 帧的成员
    BulkHead { len: usize },   // bulk 预告头：其后 len 格属于同一帧
}
```

环形缓冲的单元类型因此是 `SlotMsg<T>`；公开 API 只呈现载荷 `T`。

**发送侧**（两端一致）：

| 入口 | 占用格数 | 行为 |
| --- | --- | --- |
| `send(item)` | 1 | 预留 1 格、写入 `Payload(item)`、提交 |
| `fill_bulk(n, f)` | `n + 1` | 预留 `n+1` 格、写 `BulkHead{len:n}`、把 [`BulkWriter`] 交给 `f` 填成员 |

**空洞的补齐位置**：`BulkWriter` 的 `Drop` 把本帧未填的成员格补成 `Void`。也就是说
空洞是在**生产者收尾时**补的，而不是在预留后、交给生产者之前预填充。

> 这与「预填充」在效果上等价（提交区间同样全部已初始化），但有两点好处：
> ① 不需要在段内「先推进偏移、再反向写入已被消费的格」这种别扭操作；
> ② **panic 展开路径也覆盖**——栈展开会跑 `Drop`，帧仍被补成「已写前缀 + 空洞尾巴」。

**读端**：`recv()` / `next_async()` 在内部消化协议——

```text
Payload(t)      → 产出一条载荷 t
Void            → 丢弃、视作已读（若在帧内则成员数 -1）
BulkHead{len}   → 记录本帧还剩 len 个成员格，不产出
```

因此空洞与帧头**绝不交给最终调用者**；`MpscReceiver`/`SpscReceiver` 各自持有一个
`pending_` 计数来跟踪帧内位置。

**写锁**：`MpscSender` 的所有写入口都经 `with_write_lock_`——持写许可 → 取位 → 写入
→ 段 drop 提交 → 释放。段的生命周期被完全限制在闭包内，**「两位写者同时持有写位置」
在类型层面已无法表达**，先前的重叠缺陷因此结构性消失。

### 8.2 连带简化（本轮收益）

| 简化 | 原因 |
| --- | --- |
| 公开类型不再带缓冲类型参数 `B` | 队列总是自带 `Owned<[MaybeUninit<SlotMsg<T>>], A>` |
| 不再需要 `extend_write_segm_` / `extend_read_segm_`（唯一的两处 `transmute`） | 读端产出 `T`（move 出来）、写端产出**写票**（自持核心句柄），都不借用半部 |
| 不再暴露任何段类型 | 协议载体的单元是私有枚举，段无法作为公开类型出现 |
| `BulkWriter` 取代 `SegmMut` 薄封装 | 每格带判别式，`&mut [MaybeUninit<T>]` 连续切片不再存在；改为逐条 `push` |

## 9. 补充：`send_async` / `fill_bulk_async`（本轮补做）

先前只提供了同步写入口与「写票」，缺一个能在**锁上 / 空间上真正等待**的异步发送
入口。现在两端都补上：

| 队列 | 同步 | 异步 |
| --- | --- | --- |
| SPSC | `send` / `fill_bulk` | `send_async` / `fill_bulk_async` |
| MPSC | `send` / `fill_bulk` | `send_async` / `fill_bulk_async` |

### 9.1 语义

* `send_async(item)`：队满时 `await` 空间；MPSC 下同时 `await` 写入位（等空间也持写
  许可，与「锁覆盖全程」保持一致）。成功即消息**已提交**。
* `fill_bulk_async(n, f)`：先等够 `n + 1` 格并拿到写入位，**之后**才调用 `f`。
  这样闭包不会被「等不到空间」白白消耗——这是它相对「先跑闭包再 try」的关键优势。
* 两者都由 `gen_may_cancel_future` 生成，因此支持 `may_cancel_with`（AGENTS.md §4）；
  取消时消息**不入队**，`fill_bulk_async` 则**不调用闭包**。

### 9.2 一个实现要点：消息必须能「交还」

异步重试会反复尝试预留，因此**不能在中途丢掉消息**。为此把段写入工具改为可交还：

```rust
fn push_msg_<T, R>(segm, msg: SlotMsg<T>) -> Result<(), SlotMsg<T>>;   // 满则原样退回
fn push_payload_<T, R>(segm, slot: &mut Option<T>) -> bool;            // 满则放回 slot
```

异步路径始终把消息留在 `Option<T>` 里，**只有真正写进环里才移走它**；`fill_bulk_async`
同理把闭包留在 `Option<F>` 里，预留守卫成功后才 `take`。

### 9.3 新增用例

| 用例 | 钉住的性质 |
| --- | --- |
| `spsc_send_async_waits_then_succeeds_` | 队满时真的 `Pending`，读端腾出空间后成功 |
| `spsc_send_async_cancelled_does_not_enqueue_` | 取消 ⇒ `Cancelled` 且消息不入队 |
| `spsc_fill_bulk_async_full_` | 异步 bulk 完整交付 |
| `mpsc_send_async_waits_then_succeeds_` | MPSC 异步发送的等待/唤醒 |
| `mpsc_concurrent_send_async_keeps_all_` | 两写者异步各发 3 条，一条不少不重 |

## 10. 修正：`send_async` 的语义定位与 `close`

### 10.1 `send_async` 不需要「多遍尝试」

初版 `mpsc_send_async_` 是这样写的：`try_lock` 拿写入位 → 失败就 `Stuffed` → 外层
重试；等空间时还要先让出写入位再重来。**这是把两件事混在了一起**：

* 写锁已经覆盖「取位 → 写入 → 提交」全程，**写者一旦拿到许可，空间就是它的**；
* 因此「拿不到许可」只该 `await` 一次（等锁），而不是 try + 重试；
* 唯一需要第二段等待的是**队满**，而等空间同样在许可之内进行。

现改为：**取一次写许可**（真正 `await`，不是 `try`），之后在同一个许可之内循环
「试预留 → 队满就等空间 → 再预留」。许可在手，等空间醒来后空间必然归本写者，因此
不存在「被别人抢走再重来」这种多遍尝试。

```rust
let mut sess = shared.write_queue_.acquire_session();
let _guard = sess.write_async().may_cancel_with(cancel.child_token()).await?;  // 只等一次
let prod = unsafe { shared.produce_() };                                       // 许可在手
loop {
    match prod.try_write(&demand) { Ok(segm) => { 写入并提交; return Ok(()) }
                                    Err(Stuffed) => { prod.write_async(..).await; }  // 持锁等空间
                                    Err(e) => return Err(e) }
}
```

同步入口 `send` / `fill_bulk` 仍是 try 语义（拿不到锁返回 `Stuffed`），这是「同步不
阻塞」的自然含义；需要等待就用 `*_async`。

### 10.2 空洞的职责被写清楚了

之前文档把「空洞」讲得像是在兜并发竞争，这是**重心放错了**。写锁覆盖全程之后：

* 取位 / 写入 / 提交之间**没有 `await`**，取消打断不了它；一次 `send` 也不会写一半；
* 所以空洞**不是**为竞争准备的，它防的是**生产者在填连续段中途失败**——`BulkWriter`
  的 `Drop` 在栈展开时把未填的格补成空洞，于是本帧整体提交后，读端仍能拿到**已写好
  的前缀**。

结论：**竞争交给锁，空洞交给放弃 / 崩溃兜底**，两者职责不重叠。

### 10.3 `close` 改为异步（并补上「写者消失即关闭」）

原同步 `MpscSender::close` 用 `with_write_lock_`（try-lock）且**丢弃了返回值**，写入位
被占时它其实**什么也没做**——这是个实打实的缺陷。更要紧的是「关闭与投递」的关系：

* 若有写者已占位、尚未提交，同步关闭会让读端在它提交之前看到 EOF，那条消息**永远
  送不到**；
* 因此新增 **`close_async`**：先 `await` 写入位（= 等所有在写的写者提交完），再关闭；
* MPSC 的同步 `close` 改为返回 `Result<(), ChannelError>`，写入位被占时返回 `Stuffed`
  （明确「本次未生效」），而不是假装成功；
* 新增 **写者消失即关闭**：`SpscSender::drop` 与 `MpscShared::drop`（最后一份写者引用
  消失时）都会关闭写端，读端不会永久挂起。

### 10.4 新增用例

| 用例 | 钉住的性质 |
| --- | --- |
| `mpsc_close_async_keeps_committed_messages_` | 关闭前已提交的消息一条不丢，之后才是 EOF |
| `mpsc_drop_all_senders_closes_channel_` | 最后一个写者消失即关闭，读端不挂起 |
| `spsc_drop_sender_closes_channel_` | SPSC 同理 |
| `spsc_close_async_cancelled_keeps_open_` | 取消 `close_async` 不关闭、仍可发送 |

## 11. 定稿：`try_*` / `*_async` 命名，`BulkWriter` 改为返回值

### 11.1 命名与等待语义

| 单体 | 批量 | 等待行为 |
| --- | --- | --- |
| `try_send` | `try_send_bulk(n)` | 只**抢一两次**写入位，抢不到就返回 `Stuffed` |
| `send_async` | `send_bulk_async(n)` | 真正 `await`：MPSC 等写入位 + 等空间，SPSC 只等空间 |

### 11.2 `BulkWriter` 是**返回值**，不是闭包参数

初版把批量写成 `fill_bulk(n, |w| ...)`。这不必要地把「填充」也包进了调用里，而且
批量路径无法像单体那样「拿到写入位后再同步操作」。现改为：

```rust
let mut w = tx.try_send_bulk(n)?;   // 或 tx.send_bulk_async(n).await?
w.push(item);                        // 同步填充
// w drop ⇒ 提交整帧（未填的成员格补成空洞）
```

### 11.3 MPSC 的 bulk 段 = 写段 + **占住写入位**（一个结构性要点）

先厘清一个容易混淆的点：**「持有 `SegmMut`」并不等于「占住写入位」**。原因在底层：

* `Producer::try_write` 只借出坐标，**不推进写位置**；
* 写位置 `wp` 要等段 drop 时才由 `advance_write` 推进。

所以只把段交出去、把锁放掉，下一位写者读到的仍是同一个尚未推进的 `wp`，两段重叠。
实测（临时把写许可从填充器里拿掉，其余不动）：

```text
thread '...::mpsc_bulk_writer_holds_the_write_slot_' panicked:
  写入位被写者 1 占着: ()          # 写者 2 的 try_send 竟然成功了
```

因此 `BulkWriter` 会脱离方法返回、由调用者在任意时刻填充，**占位必须随它一起活到
drop**。于是 `MpscBulkSegm` 需要同时持有：

* 写段（负责提交写位置）、
* 写入位的写许可（`WriterGuard`）、
* 其借用的会话（`CooperativeAcqSession`）。

命名上不再另立「许可」这一层概念：对外它就是 [`BulkWriter`]（一个 bulk 段），
内部类型按段的词汇命名为 `SpscBulkSegm` / `MpscBulkSegm` / `TrBulkSegm`。

后两者构成自引用。做法是把会话放进 `Box`（地址稳定），并把 guard 的借用延长到与该
段同寿；安全性由**字段顺序**补足：

```text
segm_  →  guard_  →  sess_  →  _keep_
提交整帧   释放写入位   释放会话   释放核心句柄
```

**顺序不能反**：若先放锁再提交，别的写者会以尚未推进的写位置预留，两段重叠。
测试 `mpsc_bulk_writer_holds_the_write_slot_` 钉住这一点——写者 1 的填充器还活着时，
写者 2 的 `try_send` 必须拿到 `Stuffed`。

### 11.4 一个实现约束：`Demand` 的生命周期

`Producer::try_write<'f>(&'f mut self, demand: &'f Demand<usize>)` 要求 `demand` 与
返回的段同寿。段现在会**放进返回值**，所以 `Demand::exactly(n)`（`n` 是运行期值、
只能放局部变量）用不了。改用 `'static` 的
`static BULK_DEMAND_: Demand<usize> = Demand::at_least(1)`（有多少要多少），并在
预留前用 `free_size() >= n + 1` 自己把「够不够」判掉；提交格数由已写入量决定，
多预留的部分不会被提交。

## 12. 修正（重要）：SPSC 写票是一处实现错误，已删除

### 12.1 错误本身

`SpscWriteTicket` 持有一份**独立的** `Shared<CircCore>` 句柄，并用它调
`CircCore::try_write_(&self)`——注意是 **`&self`**。而 `Producer::try_write(&mut self)`
之所以存在，恰恰是为了不让人拿到这个 `&self` 入口。

于是 SPSC 的独占性被整个抽掉，**两段可以同时存活**：

```rust
let t = block_on(tx.next_async())?;   // 票：持有独立核心句柄，不借用 tx
let mut w = tx.try_send_bulk(3)?;     // 活段 S1（已预留、未提交），借用 &mut tx
t.send(42);                           // 票走 &self 路径 ⇒ 从同一个 wp 再开一段 S2
```

`w` 还活着时 `t.send(42)` **编译得过**（票不借 `tx`）。S1 与 S2 来自同一个尚未推进的
`wp`，`create_write_segm` 为两者各造一份 `&mut [MaybeUninit<T>]` 且区域重叠
⇒ **别名 UB**。

### 12.2 性质：不是风格问题，是滥用同 crate 信任

* `CircCore` 在 crate 外**既命名不了也构造不出来**，因此 `try_write_` 没有任何合法
  外部调用者；
* 我为了让写票能用，把 `core_` 提到 `pub(crate)`，从而让 `channels` 调到了它——
  **我是唯一那个不该存在的调用者**；
* `try_write_at`（`pub(super)`）我从未调用，只是引用它的实现来说明语义。

### 12.3 修复

* **删除** `SpscWriteTicket`、`SpscSender` 的 `TrAsyncIterator` 实现、
  `SpscSendNextAsync` 与 `spsc_send_next_async_`，以及 `SpscSender.core_` 字段；
* SPSC 的写入口因此只剩 `&mut self` 一路（`try_send` / `try_send_bulk` /
  `send_async` / `send_bulk_async`），独占性回到**借用检查器**手里；
* `channels` 对核心写入口的调用**归零**；
* 仍保留的 `pub(crate)` 只剩：`CircCore::{capacity, free_size, data_size}`
  （MPSC 免锁观察尺寸——写者持有 `&mut Producer` 期间再凭空造 `&Producer` 就是别名
  UB，只能走核心句柄）、以及用于命名类型的 `core_` / `reclaim_` / `abs_comp_`。

### 12.4 回归防护

在 `SpscSender::try_send_bulk` 的文档里加了 `compile_fail` 用例：段还活着时再借写端
必须编译失败。`cargo test --doc` 会验证它**确实编译不过**，因此这条不变量若再被
破坏（例如有人又让 `Item` 持有核心句柄），文档测试会失败。

### 12.5 代价（如实记录）

* SPSC 的写端不再实现 `TrAsyncIterator`（读端仍然实现）。写端的等待需求由
  `send_async` / `send_bulk_async` 覆盖；
* MPSC 的写端仍实现（`MpscWriteTicket`），因为它的票走**写锁**——写锁本来就是 MPSC
  序列化写者的那道防线，票不能绕开它。

## 13. 去除 `Box`：写入位许可不再需要装箱

### 13.1 问题

`channels` 里有三处堆分配，全部是 `Box`，而且都在**每次写操作**上：

1. `BulkWriter` 用 `Box<dyn TrBulkSegm<T>>` 抹平 SPSC / MPSC 两种填充器；
2. `MpscBulkSegm` 用 `Box<SessOf<'a>>` 给会话一个稳定地址（自引用 guard）；
3. `Box::new(state)` 把填充器状态搬到堆上。

`Producer` 的语义本来是够用的，这些都是我为了绕开「守卫借用会话」这一步付出的代价。

### 13.2 为什么不再需要它们

**(1) 段类型本来就相同。** SPSC 与 MPSC 用的是**同一个** `CoreOf<T, A>`（都是被动 ×
被动拓扑），所以段的类型完全一致：

```rust
ReclSliceMut<'a, SlotMsg<T>, WriterReclaim<'a, CoreOf<T, A>>>
```

于是 `BulkWriter<'a, T, A>` 直接**按值**持有段，不再需要 trait object 抹平；
SPSC 与 MPSC 的差别只剩「有没有一个占位许可」，用一个 `Option<GuardOf<'a>>` 表达即可。

**(2) 会话不需要堆。** 核查过 `atomic_sync`：没有任何 owned 守卫，所有
`WriterGuard<'a, 'g, ..>` 都借一个 `CooperativeAcqSession`，而 `release_writer` 是
`pub(super)` 拿不到。但会话**不持有状态**——

```rust
/// 一次上锁会话：它只是外壳的借用，本身不持有任何状态。
pub struct CooperativeAcqSession<'a, T: ?Sized, D, B, O>(&'a CooperativeRwLock<T, D, B, O>);
pub const fn new(lock: &'a CooperativeRwLock<T, D, B, O>) -> Self;
```

它只需要一个「比守卫活得久」的落脚点。`MpscSender` 自己就是：

```rust
pub struct MpscSender<T, A> {
    shared_: Shared<MpscShared<T, A>, A>,   // 堆分配：构建期一次
    sess_: SessOf<'static>,                  // 只借用上面那块分配里的锁
}
```

锁在 `Shared<MpscShared>` 所指的堆分配里，**地址固定不动**；会话是该发送端的字段，
只在该发送端的借用存活期间使用，因此绝不会比它指向的锁活得久。守卫的第二个生命
周期就是「发送端借用」的寿命：

```rust
pub(super) type GuardOf<'a> =
    WriterGuard<'static, 'a, (), usize, AtomicUsize, StrictOrderings>;
```

`BulkWriter` 于是按值持有「段 + 许可」，字段顺序保证 drop 时**先提交、后放位**。

### 13.3 还剩的分配（如实记录）

`channels` 现在唯一的堆分配是构建期那一处：

```rust
let shared = Shared::new(MpscShared { producer_, core_ref_, write_queue_, .. }, A::default());
```

它无法去掉：`MpscSender` 必须可克隆，而一个环只有一个 `Producer` 半部、一个写游标，
`Producer` 本身不可克隆，多写者只能共享它。**运行期（每次收 / 发 / 等待）零分配。**

### 13.4 验证

```

cargo test --doc   # 3 passed; 2 ignored；另有 1 个 compile_fail 通过
cargo clippy --all-targets  # 零告警
```

## 14. 根因修正：锁应当**保护 `Producer`**，而不是「锁 + `UnsafeCell<Producer>` 并列」

### 14.1 前面几轮全都在治表

从 §13 起我一直在给「`UnsafeCell<Producer>` + 一把独立的 `()` 锁」这个布局打补丁：
先把它塞进 `MpscBulkSegm`（`Box` 自引用），再改成把会话放进 `MpscSender`（`transmute`
伪造 `'static` 寿命）。两次都是在绕同一个错误布局。

正确的做法只有一句：**让锁去保护 `Producer`**。

```rust
type LockOf<T, A> = CooperativeRwLockOwned<ProducerOf<T, A>>;

struct MpscShared<T, A> {
    lock_: LockOf<T, A>,                       // ← 保护 Producer 本身
    core_ref_: Shared<CoreOf<T, A>, A>,        // 免锁观察尺寸 / 最后一位写者关边
}
```

因为 `WriterGuard` 实现了 `DerefMut<Target = T>`：

```rust
impl DerefMut for WriterGuard<'a, '_, T, D, B, O> {
    fn deref_mut(&mut self) -> &mut Self::Target { self.0.deref_mut_impl() }
}
```

取得写许可**就等于**取得 `&mut Producer`。于是：

| 之前 | 现在 |
| --- | --- |
| `UnsafeCell<Producer>` + `unsafe fn produce_() -> &mut Producer`（`&self` 造 `&mut`） | **不需要**：`&mut` 是锁合法借出的 |
| `with_write_lock_` / 各处 `unsafe { shared.produce_() }`（共 7 处） | **不需要** |
| `session_of_`：`transmute` 出 `SessOf<'static>` 存进发送端 | **不需要**：会话在每个方法里就地取得 |
| `BulkWriter` 持 `Box<dyn TrBulkSegm>` / `guard_` 字段 | **不需要**：段按值持有，写许可留在方法内 |
| `MpscSender.sess_` 字段 | **不需要** |

### 14.2 为什么「返回持锁填充器」在这里根本做不成

`WriterGuard<'a, 'g, ..>` 借用一个 `CooperativeAcqSession` 值。要让它作为**返回值**
逃出方法，会话就必须比方法活得久；而锁在 `Shared<MpscShared>` 里、`Shared` 又由发送端
自己持有——把会话放进发送端，在借用检查器眼里是**自引用**，诚实写法表达不出来。

也就是说：会话/守卫分离的设计本意，就是让「**持有**许可」不越出取得它的作用域。
`session.try_write(&mut self)` 的可变借用就是这条约束的载体。想绕开它，只能伪造寿命
（`transmute`）——那正是前两轮我做的事，也正是你指出的「绕过借用检查、给自己留死锁
风险」。

因此 MPSC 的 bulk 入口改为**接收同步闭包**：

```rust
tx.try_send_bulk(n, |w| { w.push(a); w.push(b); })?;      // 填充在许可保护之下
tx.send_bulk_async(n, |w| { .. }).await?;
```

闭包不能中途 `await`；持锁跨 `await` 会让争同一把锁的写者永久等待。**SPSC 不同**：
它没有锁，段按值交出去即可，因此仍返回 `BulkWriter`——那份独占性由借用检查器保证。

### 14.3 结果

| 指标 | 之前 | 现在 |
| --- | --- | --- |
| `channels` 内的 `unsafe` | 11 处（其中 7 处是 `produce_()` 调用） | **4 处**：1 处「最后一位写者关边」+ 3 处 `MaybeUninit` 位拷贝（`segm_.rs`） |
| `channels` 内的 `Box` | 3 处（每次写操作都分配） | **0** |
| 伪造成 `'static` 的会话 | 1 处 | **0** |
| 写许可逃逸出方法 | 是（返回值） | **否** |

剩下那处 unsafe：

```rust
// Drop for MpscShared：最后一位写者消失 ⇒ 关闭写端，读端才会读到 EOF。
// SAFETY: 本结构正在销毁，Shared 引用计数已归零，不存在其他持有者与并发访问。
unsafe { (*self.lock_.as_mut_ptr()).close() };
```

```

cargo clippy --all-targets  # 零告警
cargo test --lib            # 75 passed; 0 failed; 2 ignored
```

## 15. `close_async` 交给 `Producer` 自己的异步关闭

### 15.1 我原来的做法是手搓

```rust
// 之前（错）
let _guard = sess.write_async()...await?;
guard.close();            // 只落了标志，没做「关闭前给消费端发信号」
```

`Producer` 本来就提供了语义完整的关闭入口：

```rust
pub fn close(&mut self) { self.core_ref_.close_tx(); }

/// 异步关闭写端：先关闭写端，再异步排空主动消费端的残留数据。
pub fn close_async<'f>(&'f mut self) -> ProducerCloseAsync<'f, 'f, C, B, T, A>;

// spsc_.rs
async fn producer_close_async_(producer, cancel) {
    producer.core_ref_.close_tx_async(cancel).await;      // 核心这一层：
}
// core_.rs
async fn close_tx_async<K>(&self, cancel: K) { self.close_tx(); self.drain_output_async_(cancel).await; }
```

「关闭前必须给消费端发协议信号、保证它收得到」这件事就是 `close_async`（先落标志、
再排空）在做。所以两个队列的写端 `close_async` 现在都只是**持着写许可把
`Producer::close_async` 走完**，不再自己拼流程（MPSC 之所以还要先拿写许可，是为了
保证「此前提交的消息都已经在环里」——那是本层独有的顺序要求）。

### 15.2 取消语义（实测校准）

先按文档写了「取消后关闭标志仍已设置」，实测不成立：`gen_may_cancel_future` 生成的
`may_cancel_with` 在令牌**已经就绪**时根本不会轮询内层 future，因此 `close_tx()` 从未
执行。校准后的语义：

| 时机 | 结果 |
| --- | --- |
| 关闭**尚未开始**就被取消（含 MPSC 还没拿到写入位） | 返回 `Cancelled`，什么都不做 |
| 关闭**已开始**（标志已落下）后取消 | 只中断「等主动消费端排空」，**不撤销关闭** |

用例 `spsc_close_async_cancelled_keeps_open_` 钉住前者。

### 15.3 顺带修掉一个哑弹

两个读端的同步 `close()` 原来是这样的：

```rust
pub fn close(&mut self) {
    let mut fut = self.inner_.close_async();
    let _ = (&mut fut,);          // 只是构造了 future 然后又丢掉 —— 什么都没做
}
```

它**根本不生效**。读端在上游只有异步的 `Consumer::close_async`（其实现是
`core_ref_.close_rx()` 加上对主动生产端的泵），没有同步入口，所以这两个哑弹直接删除，
不保留一个骗人的 API。这是本轮的一处公开 API 删除，已在此记录。

## 16. 补上协议里漏掉的一条：`SlotMsg::Closing`

### 16.1 漏在哪

设计 `SlotMsg` 时我只考虑了「载荷 / 空洞 / 预告头」，**把「写端关闭」做成了带外状态**
（核心里的 `TX_CLOSED` 标志）。带外状态天生带有「谁先谁后」的竞态：读端在
`ready == 0` 且看到标志时就认定 EOF，而一个**已预留、未提交**的写段不在 `ready` 里
——于是关闭者与在写的写者之间必须有额外的顺序保证（我先前是靠「关闭前先拿写许可」
来补的）。

**关闭本身就是内部协议消息的一部分。** 补上第三个变体之后，EOF 变成**带内**信息：

```rust
pub(super) enum SlotMsg<T> {
    Void,
    Payload(T),
    BulkHead { len: usize },
    Closing,          // ← 新增：写端关闭前放进环里的最后一条协议消息
}
```

### 16.2 由此得到的性质

* 读端按顺序读到 `Closing` 时，**排在它前面的载荷必然已经交付**——这就是
  「关闭前必须给消费端发协议信号，保证客户端收到」的落点，不依赖带外标志的时序；
* 写者持写许可放信号 ⇒ 信号之后不可能再有写者插入；
* `TX_CLOSED` 标志的职责**收窄**为「让写端停止取位」，不再承担 EOF 语义。

### 16.3 落点

`close_async`（两端）现在做两件事，顺序不可颠倒：

1. **发信号**：预留 1 格、写入 `SlotMsg::Closing`、提交；环满时先等空间——这正是
   这个入口必须是**异步**的原因之一；
2. **落标志并交给 `Producer::close_async`**：完成排空 / 对主动消费端发协议信号。

同步 `close()` 仍然只落标志（无法等空间），属于尽力而为的快捷路径；
`recv()` 读到 `Closing` 直接返回 `Err(ChannelError::Closing)`。

### 16.4 验证

新增 `spsc_close_async_signal_is_in_band_`：先发 3 条再 `close_async`，读端必须
「3 条全到，然后才是 EOF」。

```
cargo test --lib   # 76 passed; 0 failed; 2 ignored
cargo test --doc   # 3 passed; 2 ignored；1 个 compile_fail 通过
cargo clippy --all-targets  # 零告警
```

## 17. 关闭机制统一：两端共用同一条路径（含 `Drop`）

### 17.1 抽出的共用件（`segm_.rs`）

```rust
/// 上载半部：两个队列共用。
pub(super) type ProducerOf<T, A> = Producer<BufConsumer<Msg<T>>, BufOf<T, A>, Msg<T>, A>;

/// 尽力放 Closing（非阻塞）：Ok(true) 已提交 / Ok(false) 环满 / Err 已无意义。
pub(super) fn try_push_closing_<T, A>(prod: &mut ProducerOf<T, A>) -> Result<bool, ChannelError>;

/// 放 Closing，环满时等空间再试。
pub(super) async fn push_closing_wait_<T, A, C>(prod: &mut ProducerOf<T, A>, cancel: C) -> bool;
```

关键是它们都只要 `&mut Producer`：
* SPSC 靠 `&mut Producer` 的独占借用拿到写权；
* MPSC 在写许可之下拿到 `&mut Producer`。

**拿到之后要做的事完全一样**——这正是两个 channel 该待在同一个 crate 里的理由。

### 17.2 五条关闭路径，现在同一套

| 路径 | 做法 |
| --- | --- |
| `SpscSender::close_async` | `push_closing_wait_` → `Producer::close_async` |
| `MpscSender::close_async` | 取写许可 → `push_closing_wait_` → `Producer::close_async` |
| `SpscSender::close`（同步） | `try_push_closing_` → `Producer::close` |
| `MpscSender::close`（同步） | 持写许可 → `try_push_closing_` → `Producer::close` |
| `Drop`（两端） | `try_push_closing_` → `close` |

同步入口与 `Drop` 放不下信号时（环满）退回标志位的**带外 EOF**兜底；异步入口一定能把
信号放进去（会等空间）。

### 17.3 验证

新增两个结构性用例（`spsc_/mpsc_drop_sender_puts_closing_signal_in_band_`）：发 2 条后
drop 写端，读端 `data_size()` 必须是 **3**（2 条载荷 + 1 条关闭信号）——证明 `Drop`
路径确实把信号放进了环里，而不是只落标志。

```
cargo test --lib   # 78 passed; 0 failed; 2 ignored
cargo test --doc   # 3 passed; 2 ignored；1 个 compile_fail 通过
cargo clippy --all-targets  # 零告警
```

## 18. 测试改在**真实异步运行时**里跑（tokio + compio 各一遍）

### 18.1 之前错在哪

`channels` 的测试全都自己 `futures_lite::future::block_on(...)`，两个「park」用例甚至
`pin!` + `Context::from_waker(Waker::noop())` 手动轮询、直接断言 `Poll::Pending`。
问题不是「跑不起来」，而是**测的是我假设的世界**：

* `block_on` 不是真实任务调度，waker 的传递路径、被唤醒的时机都和真实运行时不同；
* 手动轮询配 `noop` waker 时，任何「被唤醒」的语义都被架空了——真实代码不会这样驱动
  future。

### 18.2 现在的形态

仓库里既有的约定是 `#[tokio::test]` / `#[compio::test]` 各写一遍。这里用一个薄宏把
「同一个异步用例跑两种运行时」这件事收成一行：

```rust
macro_rules! dual_runtime_test_ {
    ($name:ident) => {
        mod $name {
            #[tokio::test]  async fn tokio_()  { super::$name().await }
            #[compio::test] async fn compio_() { super::$name().await }
        }
    };
}
```

用例本身写成普通 `async fn`，需要并发就 `futures_util::join!`，需要让出就
`futures_lite::future::yield_now().await`——**该 await 就 await**，不再手撸轮询。

两个原「park」用例改写为真实并发：把「发送」与「先让出一次、再读走两条」放在同一个
运行时任务里 `join!`；若 `send_async` / `next_async` 不等待而是立刻失败，用例就会失败。

### 18.3 结果

```
cargo test --lib channels::   # 64 个用例，每个都有 compio_ / tokio_ 两份
cargo test --lib              # 110 passed; 0 failed; 2 ignored
cargo test --doc              # 3 passed; 2 ignored；1 个 compile_fail 通过
cargo clippy --all-targets    # 零告警
```

`channels` 的测试里已无 `block_on`、无 `pin!`、无 `Poll::`（仅在文档文字中提到）。
