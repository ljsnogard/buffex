# `wake_slot_` 的读是否真被 STNDBY 标志保护？——审计与多线程复现

日期：2026-10-01 02:55
涉及：`src/ring/half_.rs`、`src/ring/ring_core_.rs`、`src/ring/tests_.rs`
前置：[ring-20261001-0225.md](ring-20261001-0225.md)

## 1. 问题

`RingHalf_::wake_slot_` 是普通字段 `Option<Waker>`（非原子）。对端在 `Consumer::wake` /
`Producer::wake` 里读它，且调用点都由状态字里的 `CONSUMER_STNDBY` / `PRODUCER_STNDBY`
标志把关。由此有一个印象：**对 `wake_slot_` 的读是被 STNDBY 标志保护的**。

审计结论：**不成立**。标志是「要不要去碰槽位」的前置判断，不是同步原语，也没有与槽位建立
happens-before。`RingState.atm_flag_`（`AtomicFlags<usize>`）与 `opt_demand_`
（`AtomexPtrOwned`）都走 `StrictOrderings` → SeqCst，所以问题不在内存序，而在**操作顺序与
协议本身**。

## 2. 六条依据

1. **发布顺序反了**。等待侧先发布意图、后注册 waker：`ring_read_async` 在
   `ring.buf_stat_.set_consumer_standby_()`（`ring_core_.rs`）之后才 `park_async(..).await`，
   而 `*slot = Some(cx.waker().clone())` 在 `poll_park_future_` 的首次 poll 里。SeqCst 的
   CAS 只 release **它之前**的写；槽位的写发生在它之后，因此「对端 acquire 到标志 ⇒ 能看到
   waker」这条链不存在。
2. **等待侧 TOCTOU**：`try_read_`（检查条件）→ `set_consumer_standby_()` 之间没有复检。
   对端若在这段里提交，它的快照里标志还是 0 → 不唤醒；等待者随后置位并 park → 永久挂起。
3. **唤醒侧 TOCTOU**：对端看到标志后去读槽位，而槽位可能仍是 `None`（等待者还没 poll）或上
   一轮的残留 → 直接 return；等待者随后注册 waker 并 park → 永久挂起。因为 `release_()`
   每轮都会把槽位清回 `None`，这不是罕见态。
4. **槽位本身是数据竞争**：`Option<Waker>` 是两个字（数据指针 + vtable），对端读、持有者写
   （`poll_park_future_` / `release_`），没有任何原子或互斥 → UB；撕裂读最坏会拿到无效
   vtable。`Ring` 有 `unsafe impl Send/Sync`，`split` 之后两半本来就可以分属两个线程。
5. **标志只是快照，不是临界区**：`advance_write` / `advance_read` 用的是位置 CAS 返回的
   **旧值**来决定要不要唤醒，而槽位是在更晚的时刻读的；这期间持有者完全可以清标志、重注册。
   更关键的是 `clear_*_standby_()` 只在 `DropGuard` 里调用一次（整个 `ring_*_async` 结束时），
   所以标志的实际语义是「这个操作**曾经**进入过 standby」——它跨越多轮 park/唤醒一直置位，
   期间持有者是活动的。
6. **`opt_demand_` 的对象生命周期无保护**：指针是原子的，但 `ptr.as_ref()` 之后持有者可以
   `reset_demand_()` 并让调用者的 `Demand` 析构 → use-after-free。`Drop` 里的 `release_`
   把窗口从「永久残留」缩到「并发窗口」，但没有消除。

## 3. 「最多两线程 + standby 之后不活动」这个前提

* 这是 SPSC 的设计意图，审计按它做的；它确实排除了多等待者、等待队列、ABA 等复杂度，也让
  修复可以只用「单槽原子 waker」而不是锁。
* 但它**不能**救当前代码：第 2、3 条只需要两个线程、一个等待者就能触发，而且恰恰发生在
  「进入 standby」这个瞬间——等待者此刻正在写槽位，并不安静。
* 第 5 条进一步说明「standby ⇒ 不活动」不成立：标志在整个异步操作期间常亮。

## 4. 多线程复现（本次新增的两个用例）

`src/ring/tests_.rs` 末尾新增 `wakeup_stress_tokio_` / `wakeup_stress_compio_`：

* **负载形状**：容量 2 的环，两端各搬 `STRESS_CHUNK == 2` 个元素/轮，于是写端每轮写满、读端
  每轮取空，严格交替；每一次唤醒都是「一次性」的——丢掉任何一次，两端同时停在 park 上
  （写端等空间、读端等数据），由兜底超时暴露并打印两端进度。
* **真并行**：`futures_util::join!` 逐个 poll 两个 future，窗口内不会切换任务，因此抓不到；
  必须让两端跑在两个 OS 线程上。每个线程各建一个运行时（tokio `current_thread` / compio
  `Runtime`）后 `block_on` 一个方向。
* **为什么不用 `#[tokio::test(flavor = "multi_thread")] + tokio::spawn`**：spawn 要求 future
  满足 `'static`，而 `RingReader::read_async` 的返回类型是 GAT 投影，rustc 目前证不出
  （issue #100013），包成 `BoxFuture<'static, _>` 同样失败。compio 本来就是 thread-per-core，
  没有多线程 worker 池，所以两个变体统一成「一线程一运行时」。
* **参数**：`STRESS_ROUNDS = 2000`、`STRESS_ATTEMPTS = 8`、单次尝试 `STRESS_DEADLINE = 10s`。
  多次尝试是为了同时覆盖「首次 park 撞上对端首次提交」的启动窗口与稳态里的偶发窗口。

### 实测（缺陷仍在时）

| 变体 | 结果（各跑 3 次） |
|---|---|
| tokio | 3/3 失败：第 2 次尝试 1307/2000、第 6 次 1/2000（读 0）、第 3 次 1725/2000 |
| compio | 2/3 失败：第 2 次 676/2000（读 675）、第 1 次 1/2000（读 0）；1 次通过 |

失败样本都能对上「一次唤醒被丢掉 → 两端同时 park」：`(1, 0)` 是首轮就撞上启动窗口；
`(1725, 1725)` 是稳态里的一次偶发。全量 `cargo test --lib` 现在是 **41 passed, 2 failed**
（两个压力用例），`cargo clippy --all-targets` 无告警。

### 对照实验（排除「负载本身有问题」）

把同一负载、同一参数放进**单线程** `join!`（一个 `current_thread` 运行时里 `join!` 两个
方向）：8 次尝试**全部通过**（0.54s）。这说明负载没有逻辑错误——`join!` 逐个 poll 两个
future，窗口内不会切换任务，所以协议窗口不可达；失败确实来自「两端真并行」。

## 5. 正确协议的最小要求（**已按路线 A 实施**，见 [ring-20261001-0342.md](ring-20261001-0342.md)）

SPSC + 单等待者让修复不必上锁，但需要：

1. **先注册后发布**：`slot` 写入 → 再 `set_standby()`（release 发布）；
2. **发布后复检**：置位后再查一次条件，命中即撤回注册并返回（关掉第 2 条）；
3. **槽位原子化 + 谁 CAS 谁持有**：对端用 `swap`/CAS「取走」waker 再唤醒（关掉第 3、4 条）；
4. **拆除要握手**：持有者只在确认对端不在 `wake()` 中之后才允许 `reset_demand_`（关掉第 6 条）；
5. **或更彻底**：`Demand<usize>` 是 `Copy` 小值，直接按值存进 half（或 seqlock 保护），
   消灭裸指针与悬垂。

最终实现的选择：独立 `SpinningMutexOwned` 保护等待槽（第 3、4 条的「互斥」部分），
`Demand` 按值存进登记（第 5 条），并在发布后复检（第 2 条）。第 1 条在新实现里由「填槽与
发布同处一个临界区」覆盖。

## 6. 结果

* 是否改协议：**已改**（路线 A，见 ring-20261001-0342.md）。
* 两个压力用例：修复后由「稳定复现（tokio 3/3、compio 2/3 失败）」变成 **各 10/10 通过**，
  现在是这套协议的回归验收（不再需要 `#[ignore]`）。
