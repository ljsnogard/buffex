# SPSC 唤醒协议重做：独立自旋锁保护的等待槽（路线 A）

日期：2026-10-01 03:42
涉及：`src/ring/half_.rs`（主体）、`src/ring/ring_core_.rs`、`src/ring/hook_.rs`、
`src/ring/tests_.rs`、`src/lib.rs`
前置：[ring-20261001-0255.md](ring-20261001-0255.md)（审计与多线程复现）

## 1. 决策

审计给出两条路线：

* **A（本次采用）**：`RingHalf_` 里放一把**独立的** `SpinningMutexOwned`，等待槽
  `Option<WaitReg_>` 整个包在锁里；协议改为「登记 → 发布 → 复检」，认领用状态字的 CAS
  仲裁。
* B：把锁位也塞进 `atm_flag_`，用「兴趣位 + 令牌位」两 bit 的 CAS 令牌传递。

选 A 的理由：数据区的 `rp`/`wp` CAS 是更高频的热路径，唤醒槽的锁只在「有人 park / 有人
提交且有人等待」时才被碰；多用一个独立的原子字（另一条 cache line）换取热路径不争用，更划算。
B 方案留作后续优化（收益是少一个字段与更少的原子操作，代价是同字竞争与更细的 hb 论证）。

## 2. 新协议

```
状态：interest = CONSUMER_STNDBY / PRODUCER_STNDBY（与 rp/wp 同一个原子字，SeqCst）
      slot: SpinningMutexOwned<Option<WaitReg_>>，WaitReg_ { waker_, demand_ }

等待者（park future 的首次 poll）：
  ① 锁内「填槽 + 发布兴趣位」            // 同一个临界区
  ② 复检（can_consume_ / can_produce_）  // 关掉窗口 2
       命中 → 撤回登记（锁内认领 + 取走）→ 返回 Ready(None)，调用方重试
       未命中 → 建立 cancel signal，返回 Pending
对端（提交之后，由 `TrPark::wake`）：
  ③ 锁内「按登记里的 demand 副本判定够不够 → 抢认领权（CAS 1→0）→ 取走登记」
     → 锁外 `waker_.wake()`
撤回（唤醒后清理 / 取消 / `Drop`）：
  ④ 锁内「抢认领权 → 取走」；抢不到说明对端已认领，什么都不做
```

不变式与由此关掉的缺陷：

| 审计条目 | 由什么关掉 |
|---|---|
| 窗口 2（检查 → 发布之间对端提交） | ② 发布后复检 |
| 窗口 3（发布 → 注册之间对端提交） | ① 登记先于发布 + 锁把「发布/登记」与「认领/取走」串起来 |
| 数据竞争（`Option<Waker>` 双侧写） | 槽位的所有访问都在 `SpinningMutex` 内 |
| 兴趣位「常亮」 | 兴趣位语义改为「当前有登记」，由认领方清除；`DropGuard` 删除 |
| `opt_demand_` 悬垂指针 | `Demand` 按值存进登记，对端只用副本判定 |

## 3. 改动清单

* `half_.rs`
  * `RingHalf_ { wait_slot_: SpinningMutexOwned<Option<WaitReg_>> }`，新增 `WaitReg_`；
    `with_slot_` / `publish_wait_` / `take_for_wake_` / `withdraw_` 四个原语。
  * `Consumer` / `Producer` 各加 `try_register_`（登记+发布+复检）与 `withdraw_`；
    `TrPark::wake` 改为「锁内判定+认领+取走，锁外唤醒」。
  * park future 新增 `demand_` / `state_` / `registered_` 三个字段；`poll_park_future_`
    首次 poll 走协议三步，`Drop` 在 `registered_` 为真时撤回。
  * 删掉 `opt_demand_`（`AtomexPtrOwned`）、`init_demand_` / `pending_demand_` /
    `reset_demand_` / `release_`，以及两个适配器的 `Drop`（登记已不在适配器里发生）。
* `ring_core_.rs`
  * `RingState`：`set_*_standby_` / `clear_*_standby_` → `try_publish_*_standby_` /
    `try_claim_*_standby_`；新增 `can_consume_` / `can_produce_`；`new` 与两个
    `is_*_standby_`（后者仅测试用）放宽到 `pub(super)`。
  * 两个等待循环：删掉 `DropGuard` 与 `set_*_standby_`，改传 `&ring.buf_stat_` 给
    `park_async`，并把 `as_mut_unchecked()` 换成 `as_ref_unchecked()`。
* `hook_.rs`：`TrPark::park_async` 由 `&'f mut self, demand` 改为
  `&'f self, demand, state`（**公开 trait 签名变更**；`&mut` 已无必要，顺带消除
  `Ring` 半部被 `&mut`/`&` 同时借用的别名问题）。
* `lib.rs`：移除已无人使用的 `#![feature(drop_guard)]`。

## 4. 实施中发现并修掉的问题

1. **复检命中时未撤回登记**：首版在 ② 命中时直接 `return Ready(None)`，把「槽位 + 兴趣位」
   留在 half 上；压力用例里下一次 `publish_wait_` 的 `debug_assert` 直接命中。改为在
   `try_register_` 内部两处「不要睡」的分支都先 `withdraw_`。
2. **写端单测用空环**：容量 2 的新环 `free == 2`，`at_least(1)` 的写端复检必然命中、不会
   park；改用永远不满足的下限专门测机械路径。
3. 变异校验时踩到自己的坑：`let _ = claim();` **仍然会调用** `claim()`（只是丢弃返回值），
   这是个无效变异，一开始误判成「claim 未被测试覆盖」。改成 `let _ = &claim;` 后单测立即
   抓住。记录下来以免后人重复误判。

## 5. 验证

* `cargo test`：**44 passed**（含两个之前必败的多线程压力用例）；
  `cargo clippy --all-targets` 无告警。
* 压力用例各跑 **10 次全通过**（修复前：tokio 3/3 失败、compio 2/3 失败，失败样本
  `(1, 0)` / `(1725, 1725)` 与审计窗口对应）。
* 变异校验（应被抓住的都抓住了）：

| 变异 | 结果 |
|---|---|
| 去掉发布后复检（窗口 2 回来） | 压力用例挂死 → 被超时/断言抓住 |
| 复检命中时不撤回登记 | `publish_wait_` 的 `debug_assert` 抓住 |
| 去掉认领（`take_for_wake_` 不调 `claim`） | `slot_claim_happens_exactly_once_` 抓住 |
| 去掉两个 park future 的 `Drop` 撤回 | `park_future_registers_and_withdraws_` 抓住 |
| 「先发布后填槽」（同一临界区内） | **未被抓住 —— 且它在本设计里不是缺陷**：填槽与发布同处一个临界区，对端也必须持锁才能看槽位，因此中间态不可观测。语义上仍保留「登记先于发布」的写法（不变式更直观），但它已不是正确性的必要条件。 |

## 6. 遗留

* 路线 B（把锁位并入 `atm_flag_`）未实施，留作热路径/原子操作数的优化选项。
* `advance_read` / `advance_write` 仍用位置 CAS 的**快照**判断要不要进 `wake()`；这是安全
  的（快照错过兴趣位时由等待者的复检兜住，见审计窗口 2 的论证），属于快速路径优化。
* 「漏唤醒」这类回归在压力用例里表现为挂死（由 `STRESS_DEADLINE` 兜底），不是干净失败；
  如需 CI 里秒级失败，可另加运行时无关的轮询预算（当时评估后未做）。
