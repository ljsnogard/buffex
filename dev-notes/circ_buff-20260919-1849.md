> 范围：`buffex` 的 `circular_buff` 模块（`src/circular_buff/`）。本文**只提案**公开
> API 变更，不实施（AGENTS.md §1）。未触碰 `smux_v1/`。
>
> 复现实验日期：2026-09-19 18:49（UTC）。基线提交：`3684123`（`dev/0.3.0`，
> 工作区在改动前干净）。

> 新增测试：`src/circular_buff/tests_/socket_pump_.rs`
> （注册于 `src/circular_buff/tests_/mod.rs:20`）。

## 0. 结论速览

1. 报告的两个方向都**已复现**，且比报告更严重：tokio `UnixStream` 在 reactor 尚未
   被驱动时，**首个 `poll_write` 就返回 `Pending`**，因此「被动生产 × 主动消费」
   一个字节都出不去（不是只丢尾段）。
2. 根因有两处，都在「主动端的泵」：
   - **输出侧**：提交路径只做**单次非阻塞 poll**（`Waker::noop()`），混合模式又
     **不产出任何可被调用方驱动的泵对象**（`BuildOutcome` 只给被动半部），
     `Pending` 之后没有任何执行体再驱动它；
   - **输入侧**：异步读路径虽然 `await` 主动生产泵，但该泵在搬入一批数据后
     **不交还控制权**，继续下一轮 `await` 设备；真实 socket 第二次轮询 `Pending`，
     已经把数据提交进环的读者仍然拿不到读段。
3. 「设备就绪唤醒泵」的路径**不存在**：主动端的 `WakeSlot` 只在构建期 armed，
   而唯一会往里注册 waker 的 `park_producer` / `park_consumer` 只被全主动
   `Pipeline` 调用；`fire_*` 只由**环状态**变化触发，与设备就绪无关。
4. compio socket 半边因 `SharedFd` 内部是 `Rc` 而 `!Send`，无法满足核心
   `Send + Sync` 的硬约束——这是类型层面的排除，不是实现细节。
5. 推荐：**短期**用「全被动环 + 调用方 async 泵」并把该用法写成契约（方案 C），
   同时修掉输入泵「搬完不交还」的内部缺陷；**中期**为混合模式公开可被调用方
   `spawn`/`join` 的泵 future（方案 A）。方案 B（改 `BuildOutcome` 返回类型）破坏性
   大，暂不推荐；方案 D（flush/close 钩子）只对「暂存型」输出适配器必要。

## 1. 症状与复现

### 1.1 症状

把真实异步 socket（tokio `UnixStream`）适配成 `TrInput` / `TrOutput` 后接入
`circular_buff` 的**主动端**：

| 拓扑 | 现象 |
| --- | --- |
| 被动生产 × **主动消费**（`producer_passive().pipe_into_output(...)`） | 协议写出一帧后转去读对端；提交路径单次 poll 返回 `Pending`，帧的**全部字节**留在环里，对端永远收不到 → 互相等待 |
| **主动生产** × 被动消费（`pipe_from_input(...).consumer_passive()`） | `read_async` 先 `Pending` 在设备上；设备就绪后泵把数据搬进环，但泵继续 `await` 更多数据并再次 `Pending`，读者拿不到读段 → 同样互相等待 |

两条单向「裸测试」本身没问题：环写 → `TrInput` 读（或反之）在不接主动端时正常，
这一点与报告一致。

### 1.2 如何复现

新增测试文件 `src/circular_buff/tests_/socket_pump_.rs`（真实
`tokio::net::UnixStream::pair()`，测试内部最小设备 `SockInput` / `SockOutput`
参照 `abs_buff_tokio_adapt::{ReadAsInput, WriteAsOutput}` 的写法）：

```bash
cd buffex
cargo test                                                   # 46 passed, 2 ignored
cargo test --lib socket_pump_ -- --ignored                   # 2 个 pin 均按预期失败
```

- `active_output_pump_stalls_on_partial_socket`（`#[ignore]`）：写入 4 MiB
  （环容量 8 MiB），断言 `tx.data_size() == 0`。实测失败：
  `left: 4194304, right: 0`——**全部 4 MiB 滞留**，且对端一个字节都没收到。
- `active_input_pump_stalls_on_pending_device`（`#[ignore]`）：对端 50 ms 后写入
  1 KiB，读侧 2 秒有界超时后失败——设备确实读到过 1 KiB（探针确认），但泵不返回。
- `caller_driven_pump_over_socket_works`（**保持启用、通过**）：全被动环 + 调用方
  两条 async 泵（入向、出向）用 `tokio::join!` 与场景并发，32 KiB 全量往返成功。

### 1.3 实测细节（关键）

探针（临时 `eprintln`，已移除）显示输出侧设备**只被 poll 了一次且立即
`Pending`**：

```

```

输入侧探针显示设备确实读到数据，随后泵再次 `Pending`，读者始终没有机会

```
[SockRead::poll] pending=true    ← 泵继续等更多数据，不返回
（2s 后读侧超时）
```

## 2. 根因：逐条回答

### Q1. 主动端的泵到底由哪些路径驱动？每条能否 `await` 一个 `Pending` 设备？

「泵逻辑」在主动端的 `react_async` / `pump_async`：`react_async` 是单轮搬运
（`circ_buff_.rs:731-766` / `823-858`），`pump_async` 是循环多轮
（`circ_buff_.rs:701-728` / `794-820`）。调用点如下：

| 驱动路径 | 入口 | 到设备的方式 | 能否 await `Pending` |
| --- | --- | --- | --- |
| 构建期初始化 | `builder.rs:546-563` → `dev_producer_init_async_`（`circ_buff_.rs:677-699`）/ `dev_consumer_init_async_`（`769-791`） | `poll_once` 单次（`:694` / `:786`），`Waker::noop()`（`core_.rs:270-274`） | **否**，单次非阻塞 poll |
| 写提交 | `advance_write`（`core_.rs:836-853`）→ `pump_output_sync`（`:636-674`，poll 在 `:663`） | 同上，单次 poll | **否** |
| 读提交 | `advance_read`（`core_.rs:856-872`）→ `pump_input_sync`（`:586-624`，poll 在 `:613`） | 同上，单次 poll | **否** |
| `try_write` 重试 | `try_write_`（`core_.rs:343-362`，`:358`）→ `pump_output_sync` | 单次 poll | **否** |
| `try_read` 重试 | `try_read_`（`core_.rs:387-407`，`:403`）→ `pump_input_sync` | 单次 poll | **否** |
| 同步关闭 | `close_tx`（`core_.rs:879-883`，`:882`）→ `pump_output_sync` | 单次 poll | **否** |
| 异步关闭排空 | `close_tx_async`（`core_.rs:889-895`）→ `drain_output_async_`（`:681-701`）→ `consumer.pump_async(self).await`（`:691`） | `react_async(...).await`（`circ_buff_.rs:809`） | **能**（但会置 `TX_CLOSED`，只能收尾） |
| 被动读等待 | `core_passive_read_async_`（`core_.rs:1322-1399`）→ `producer.pump_async(core).await`（`:1351`） | `react_async(...).await`（`circ_buff_.rs:717`） | **能**，但泵不交还控制权（见 R2） |
| 被动写等待 | `core_passive_write_async_`（`core_.rs:1409-1486`）→ `consumer.pump_async(core).await`（`:1441`） | `react_async(...).await`（`circ_buff_.rs:809`） | **能**，但只在 `try_write_` 失败（环满）后才走到 |
| 全主动流水线 | `Pipeline::pipe_async`（`spsc_.rs:599-644`）→ `pipe_input_once` / `pipe_output_once`（`core_.rs:1048-1071` / `1076-1100`） | 直接 `input.read_async(...).await` / `output.write_async(...).await`，不经 `react_async` | **能**（唯一「持续流动」的路径） |

**汇总**：`Pending` 安全（真正 `await`）的路径只有 4 条——
`close_tx_async`、`core_passive_read_async_`、`core_passive_write_async_`（仅环满时）、
以及 `Pipeline`。它们分别是「关闭收尾」「读需求」「写背压」「双主动」。**提交路径
（`advance_*` / `try_*` / `close_tx` / `init_async`）全部是单次非阻塞 poll。**

### Q2. 混合模式有没有任何公开 future 能持续泵主动端？

**没有。** 三个证据：

1. **构建产物只给被动半部**：`BuildOutcome` 对混合模式的两条实现分别只返回被动端
   —— 主动生产 × 被动消费 → 仅 `Consumer`（`builder.rs:631-646`）；被动生产 ×
   主动消费 → 仅 `Producer`（`builder.rs:648-663`）；只有主动 × 主动才产出
   `Pipeline`（`builder.rs:665-681`）。混合模式调用者**拿不到任何泵对象**。
2. **被动半部的公开方法里只有需求驱动的 await**：
   - `Producer::write_async`（`spsc_.rs:171-176`）只在 `try_write_` 失败（环满）后
     才 `await` 泵（`core_.rs:1424-1443`）；环未满时写段立即返回，提交时的
     `pump_output_sync` 是单次 poll。**只要调用者停止写入（等对端答复），环里未满的
     尾段就再没有 commit 去驱动它。**
   - `Consumer::read_async`（`spsc_.rs:331-336`）会 `await` 输入泵，但泵不交还
     控制权（R2），所以对 `Pending` 设备等价于挂起。
   - `Producer::close_async`（`spsc_.rs:158-160`，实现 `:261-274` →
     `core_.rs:889-895`）**确实会把残留排空**（`drain_output_async_` 里 `await`
     设备），但它同时置 `TX_CLOSED`，协议握手中途不可用；`Consumer::close_async`
     （`spsc_.rs:318-320`）只关闭读端，不驱动任何泵。
3. **被动的 `try_*` 只是单次 poll**（Q1 表），不能持续泵。

### Q3. 既有 `tests_/pump_.rs` 主动模式测试为什么通过？

假设成立：它们用的设备**永远就绪**，从不返回 `Pending`。

- `tests_/mod.rs:62` 直接复用 `abs_buff_testkit::{TestInput, TestOutput}`；
- `TestInput::read_async` 返回 `ReadySegm`（`abs_buff-testkit/src/lib.rs:250-267`），
  `TestOutput::write_async` 同样（`:295-312`）——`read_async` / `write_async` 当次
  调用即完成，单次非阻塞 poll 就搬完，因此提交路径的「单次 poll」足够；
- `pump_.rs` 里的 `GatedInput`（`:335-367`）在门未开或数据耗尽时返回
  `Ready(0)`（`:355-359`），**也不是 `Pending`**；`try_read_auto_drives_active_producer`
  正是靠这个 `Ready(0)` 让泵循环退出；
- 唯一带真实 `Pending` 语义的设备 `BlockingInput`（`pump_.rs:158-244`）只出现在
  `pipeline_flows_driven_by_devices`（全主动 → `Pipeline`）与双主动中转测试里，
  走的都是会 `await` 的 `Pipeline` 路径。

结论：`pump_.rs` 覆盖了「永远就绪设备」，但**没有覆盖**「提交路径 + `Pending`
设备」，所以缺陷不会被它们暴露。

### Q4. `Pending` 设备为什么恰好破坏混合模式契约？（唤醒路径）

一次写提交的完整路径：

```text
passive Producer 段 drop
  → WriterReclaim::reclaim (reclaim_.rs:188)
  → CircCore::advance_write (core_.rs:836-853)
  → fire_consumer (core_.rs:964-970)   // 只唤醒，不搬运
  → pump_output_sync (core_.rs:852 → 636-674)
  → poll_once(consumer.react_async(segm))   // core_.rs:661-664
  → 设备 write_async 只被 poll 一次 → Pending
  → pump_output_sync `moved == 0` → break → 返回
```

**谁在设备 future 上注册 waker？** 谁 poll 就谁注册。提交路径走 `poll_once`
（`core_.rs:270-274`），用的是 `Waker::noop()`——设备（tokio reactor）拿到的
waker 是个**空操作**；即使 socket 之后可写，唤醒也只会打到 noop。异步路径
（`pump_async`）用调用者的真 waker，所以只有它安全。

**谁会唤醒泵？** 只有两条可能的来源：

- **环状态变化**：`fire_producer` / `fire_consumer`（`core_.rs:953-960` /
  `964-970`）在 armed（`TX_STNDBY` / `RX_STNDBY`）时调用端类型的 `check`，主动端的
  `check`（`circ_buff_.rs:568-579` / `648-661`）会 `signal` 自己的 `WakeSlot`。
  但 `WakeSlot`（`circ_buff_.rs:239-243` / `306-315`）里**必须先有人注册 waker**：
  注册只发生在 `park_producer`（`core_.rs:715-741`）/ `park_consumer`（`:753-779`），
  而这两个方法**只被全主动 `Pipeline` 调用**（`spsc_.rs:636` / `:638`）。
  混合模式下 `arm_producer`/`arm_consumer`（`circ_buff_.rs:697` / `:790`，
  `core_.rs:1144-1150`）把 STNDBY 置了位，槽位却是空的——`signal` 空转。
- **设备就绪**：只有「有人正在 `await` 设备 future」时才会发生，即 Q1 表中那 4 条
  异步路径。混合模式的**提交路径根本不在其中**。

**因此：主动端的 `WakeSlot` 只被环的 `fire_*` 使用；没有任何路径会在「设备就绪」时
唤醒提交路径上的泵。** 这就是混合模式契约被 `Pending` 击穿的精确位置。

补充（输入侧的独立缺陷 R2）：`dev_producer_pump_async_`（`circ_buff_.rs:701-728`）
的循环条件是「还有可写空间」，每轮都 `await react_async`；而 `react_async`
（`circ_buff_.rs:744-765`）只要搬了 ≥1 字节就返回 `Reacted`（`:761-765`），于是泵立刻
开始下一轮、再次 `await` 设备并 `Pending`。它只在设备返回 `Ready(0)`/错误
（`:755-759`）或把整段可写区填满时才会返回。结果：数据已经 `advance_write` 进环，
调用者的 `try_read_` 却永远等不到执行机会。

### Q5. `Send + Sync` 约束在哪里？为什么排除 compio socket？

约束链（自下而上）：

- `TrCircBuffCore` 的**超类**就是 `Send + Sync`：`abs_comp_.rs:58-61`
  （`pub trait TrCircBuffCore where Self: Send + Sync`）；
- 核心的通用 impl 块要求两端 `Send + Sync`：`core_.rs:429-435`
  （另有 `:336-342` / `:381-386`）；`CircCore` 的手写 `unsafe impl Send/Sync`
  在 `core_.rs:1163-1177`；
- 构建终点 `ReadyBuilder::build_async` 要求 `P: Send + Sync`、`C: Send + Sync`
  （`builder.rs:488-494`）；`BuildOutcome` 各实现进一步要求设备满足
  `I: Send + Sync + TrInput<T>`、`O: Send + Sync + TrOutput<T>`
  （`builder.rs:633` / `650` / `668-669`）；
- 半部类型同样要求：`spsc_.rs:82-91`（`Producer`）、`97-106`（`Consumer`）；
- 因此设备随核心被 `move` 进 `UnsafeCell`（`core_.rs:328-329`）并可能跨线程，
  `Send + Sync` 是硬约束。

compio 侧：`compio_driver::SharedFd<T>(Shared<Inner<T>>)`
（`compio-driver-0.12.5/src/fd.rs:41`），而 `Shared` 在未启用 `sync` feature 时是
`synchrony::unsync::Shared = std::rc::Rc`
（`fd.rs:19-26` 的 `cfg_select!`；`synchrony-0.1.9/src/shared.rs` 的 `unsync` 模块
`pub use std::rc::{Rc as Shared, Weak}`）。compio 默认 feature 不含 `sync`
（`compio-0.19.2/Cargo.toml` 的 `default = ["runtime", "io-uring"]`，`sync` 需显式
开启），`buffex` 的 dev-dependency 也没开（`buffex/Cargo.toml` 的
`compio = { features = ["fs", "macros", "time"] }`）。故 compio socket 半边
`!Send`（连带 `!Sync`），**编译期就无法**作为 `DevProducer` / `DevConsumer` 的
设备——这正是报告第 3 点，也已记录在
`smux_v1/dev-notes/connection-20260919-1631.md` §9.2(1)。

## 3. 为什么「socket 抽象成 `TrInput`/`TrOutput` 后接入 `circ_buffer`」会出问题

正面回答人类提问的原话：

1. **混合模式没有可被调用方驱动的泵 future。** `build_async` 的 `BuildOutcome`
   对「主动 × 被动」只返回被动半部（`builder.rs:631-663`），调用者手里根本没有
   一个「持续把环搬空 / 搬满」的对象可以 `spawn` 或 `join`。
2. **提交路径的泵只做单次非阻塞 poll。** `advance_write` / `advance_read` /
   `try_*` / `close_tx` / `init_async` 全部经 `poll_once` + `Waker::noop()`
   （`core_.rs:270-274`）；对永远就绪的内存设备够用，对真实 socket 不够——
   而且实测 tokio socket 的**第一次** `poll_write` 就 `Pending`，于是「尾段滞留」
   实际表现为「全部滞留」。
3. **设备就绪时没有唤醒泵的路径。** `fire_*` 只由环状态变化触发（`core_.rs:953` /
   `964`）；主动端 `WakeSlot` 虽然 armed，却只有全主动 `Pipeline` 会注册 waker
   （`spsc_.rs:636` / `:638`）。混合模式下设备就绪的唤醒只可能发生在「有人正在
   `await` 设备」的那 4 条异步路径里，而提交路径不在其中。
4. 附加（输入方向）：即便走了异步读路径，输入泵也**搬完一批后继续 `await` 设备**
   （`circ_buff_.rs:701-728`），不把控制权交还给 `try_read_`。

相比之下，「全被动环 + 调用方 async 泵」（`smux_v1/tests/common/mod.rs` 的形态）
把「设备搬运」与「环提交」显式串在一个由运行时正常 `await` 的 future 里：设备
waker 即任务 waker，`Pending` 与就绪都由 executor 正确调度，因此可用——见新增测试
`caller_driven_pump_over_socket_works`。

## 4. 解决方案

### 方案 A：为混合模式公开可被调用方 `spawn`/`join` 的泵 future（推荐）

新增两个**加法式**公开方法（不改既有签名）：

```rust
// spsc_.rs —— 提案，未实现
impl<C, B, T, A> Producer<C, B, T, A> {
    /// 持续驱动「主动消费端」把环内数据推到输出设备，直到环空 + 对端关闭或取消。
    /// 由调用方 spawn / join；设备就绪经 await 注册的真 waker 唤醒。
    pub fn pump_async(&mut self) -> ProducerPumpAsync<'_, '_, C, B, T, A>;
}

impl<P, B, T, A> Consumer<P, B, T, A> {
    /// 对称：持续驱动「主动生产端」从输入设备拉取补位。
    pub fn pump_async(&mut self) -> ConsumerPumpAsync<'_, '_, P, B, T, A>;
}
```

内部骨架（输出侧，基于已有零件拼装）：

```rust
// core_.rs（内部）
async fn pump_output_until_idle_<K>(&self, cancel: K) {
    loop {
        // ① 有数据 / 设备可写：await 设备（真 waker），把一批数据搬出去。
        let moved = self.consumer_pump_once_await_(&cancel).await;
        if cancel.is_cancelled() { break; }
        if moved == 0 {
            if self.data_size() == 0 {
                // ② 环空：park 到主动消费端自己的 WakeSlot；
                //    生产端提交 → fire_consumer → check → signal 唤醒本泵。
                self.park_consumer().await;
            }
            // data_size > 0 且 moved == 0 ⇒ 设备 Pending，① 里的 await 已经挂起，
            // executor 会在设备就绪时重新轮询本 future。
        }
    }
}
```

要点：

- **设备就绪的唤醒**由 ① 里的 `await react_async` 承担——设备 future 注册的是
  调用者任务的真 waker；
- **环状态变化的唤醒**由 ② 的 `park_consumer()`（`core_.rs:753-779`）承担——它
  复用现成的 STNDBY armed 协议，`fire_consumer`（`core_.rs:964`）会 `signal`。
  这两者互补，覆盖「设备慢」与「生产慢」两种等待；
- 输入侧还需要把 `dev_producer_pump_async_`（`circ_buff_.rs:701-728`）改成
  **搬入一批即返回**（`moved > 0` 就 `break`，把「是否还需要更多」交回调用者的
  `try_read_` 判定），或者给 `ReceiverReact` 增加「设备暂时阻塞」语义（该枚举
  `abs_comp_.rs:120-127` 是私有模块，改动不是公开 API）。这是**纯内部修复**，
  与是否新增公开方法无关，建议优先做。

### 方案 B：让 `BuildOutcome` 的混合模式也产出可驱动的泵对象

```rust
// builder.rs —— 提案，未实现
impl<I, B, T, A> BuildOutcome<DevProducer<I, T>, BufConsumer<T>, B, T, A> for () {
    // 现行：type Output = Consumer<...>;
    type Output = (Consumer<DevProducer<I, T>, B, T, A>, ConsumerPump<I, T, B, T, A>);
}
```

- 优点：调用者天然拿得到泵，不会「忘记」驱动主动端；与全主动 `Pipeline` 对称。
- 缺点：**破坏性**——混合模式 `build_async` 的返回类型变化，所有既有调用点
  （含 `smux_v1` 之外的 `buffex_iroh` 等）都要改；且泵与半部同时借用核心，需要
  仔细设计所有权（`Producer` + 泵都持有 `Shared<CircCore>` 是可做的）。
- 结论：除非确定要长期以主动端为核心用法，否则**先用方案 A**；两者不冲突，
  A 落地后 B 只是「把 A 的返回值打包进构建产物」，可作为后续增量。

### 方案 C：把「主动端只适用于永远就绪的设备」写成契约（零 API 变更，立刻可用）

在 `mod.rs` 的「主动模式的驱动」一节（`mod.rs:94-108`）明确：

> 主动端的提交路径只做**单次非阻塞 poll**，因此**只对永远就绪（非阻塞）的设备成立**。
> 对完成式 / 真实 socket（会返回 `Pending`）设备，官方用法是
> **全被动环（`producer_passive().consumer_passive()`）+ 调用方 async 泵**。

代码骨架（与新增测试 `caller_driven_pump_over_socket_works` 和
`smux_v1/tests/common/mod.rs` 一致）：

```rust
// 环：两端全被动，不接设备
let (mut ring_tx, mut ring_rx) =
    CircularBuffBuilder::with_capacity(N)?.build_async().await?;

// 入向泵：设备 → 环
let pump_in = async {
    while let Some(n) = input.read_async(&mut buf).await.pick_left() {
        if n == 0 { break; }
        let bytes = /* &buf[..n] */;
        let mut off = 0;
        while off < bytes.len() {
            let mut segm = ring_tx.write_async(&Demand::at_least(1)).await.pick_left()?;
            off += segm.as_segm_mut().clone_items_from_buff(&bytes[off..]);
            drop(segm); // 提交 → advance_write
        }
    }
    ring_tx.close(); // 让下游读到 EOF
};

// 出向泵：环 → 设备（先上网、后释放缓冲）
let pump_out = async {
    loop {
        let Some(segm) = ring_rx.read_async(&Demand::at_least(1)).await.pick_left() else { return };
        let child = segm.as_segm_ref();
        let n = child.least_count();
        let mut dst = /* Vec<MaybeUninit<u8>> */;
        let moved = unsafe { child.move_items_to_buff(&mut dst) };
        let mut off = 0;
        while off < moved {
            match output.write_async(&dst[off..moved]).await.pick_left() {
                Some(0) => unreachable!(),
                Some(k) => off += k,
                None => return,
            }
        }
        drop(child); // 上网成功后才提交消费
    }
};

// 与协议并发（同一任务，不 spawn —— compio socket !Send）
tokio::join!(pump_in, pump_out, protocol_fut);
```

- 优点：**零代码改动即可用**，已在 `smux_v1` 冒烟测试与本 crate 新增测试中验证；
  对 `!Send` 运行时也成立（不要求 `spawn`）。
- 缺点：吞吐受泵分块限制；调用者要自己写泵；无法使用主动端的 `WakeSlot` 优化。

### 方案 D：为输出设备引入 flush/close 钩子（针对暂存型 `TrBuffWrite`）

`abs_buff_compio_adapt::CompioWriteAsBuff` 的契约是「段回收只记账，真正写盘发生在
下一次 `write_async` 或显式 `flush_async`」，而 `TrBuffWrite` 没有 flush 钩子，
于是写完最后一帧就转去读对端的调用方会双方互等（`smux_v1/...-1631.md` §9.2(2)）。

- 方案 D 的落点是把 `flush_async` / `shutdown_async` 作为**输出设备的可选契约**
  暴露出来：或者加到 `abs_buff::io::TrOutput`（跨 crate 公开 API 变更，所有适配器
  都要实现），或者在 `buffex` 侧为「主动消费端」加一个收尾钩子
  （`Producer::flush_async`），语义是「把设备内部暂存写净」而不关闭环。
- 对**真实 socket 设备**本身不必需：方案 A/C 的 `await` 已经把「提交」与「上网」
  合并在同一个 future 里。
- 代价：跨 crate 破坏性变更；建议独立议题，不与本轮 A/C 捆绑。

### 推荐方案与取舍

| 方案 | 改动面 | 破坏性 | 能解决 | 结论 |
| --- | --- | --- | --- | --- |
| C 契约 + 调用方泵 | 文档 | 无 | socket 双向、`!Send` 运行时 | **立刻执行**（官方用法） |

## 6. 与报告不一致 / 需要纠正之处

1. 报告称「主动生产 × 被动消费：socket 读返回 `Pending` 时环**从不补位**」。
   精确说法：**环确实被补了**（`advance_write` 已提交，探针看到 `filled=1024`），

   根因是「泵不交还控制权」，不是「不补位」。
2. 报告称输出侧「socket 写返回 `Pending` 时**字节**留在环里、**尾段**永不驱动」。
   实测更严重：tokio `UnixStream` 在 reactor 未被驱动时**首个 `poll_write` 即
   `Pending`**，因此在一个提交批次内是**全部字节**滞留（4 MiB 一个都没出去）。
   「尾段」现象在「设备只部分接受」时同样成立，但首因是单次 poll 本身。
3. 报告未提及但实测存在：`Producer::close_async`（`spsc_.rs:158`）经
   `close_tx_async` → `drain_output_async_`（`core_.rs:889-895`）**能**异步排空残留。
   因此「没有任何 future 能排空主动消费端」不完全准确——存在一个**收尾专用**的
   future，但它会置 `TX_CLOSED`，握手进行中不可用，也不能持续流动。
4. 报告「每条单向半边单独都能工作」：在本调查里成立的形态是「全被动环 + 裸

## 7. 追问：能否把泵写成「存在主动端内部的自驱动 future」？

**问题**：能不能把主动端泵写成一个 async 死循环——`poll_once` 拿到 `Pending` 后把
设备 future 的 waker 存进 `DevProducer`，对端每次操作时唤醒它，相当于就地做一次
主动泵？这个设想在 Rust 中现实吗？

**结论**：循环本身完全现实——它**就是**本文档 §4 方案 A 的
`Producer::pump_async()`。不现实的是「把 waker 存进主动端就能自驱动」这一步。

### 7.1 关键区分：waker 只负责「请求唤醒」，executor 才负责「重新 poll」

Rust 的 `Future` 是**惰性**的：`poll` 只会在有人调用时发生。设备 future 在返回
`Pending` 时会把 waker 注册给**它自己的 reactor**（tokio 的 IO driver、compio 的
完成队列……）。reactor 稍后调用这个 waker，语义只是「请重新 poll 我」——它**不会**
自己去 poll。真正执行 poll 的必须是**某个持有该 future 的执行体**。

所以把 waker 存进 `DevProducer` 之后：

- 如果泵循环是一个**被调用方 join/spawn 的 future**，waker 唤醒的是调用方的任务，
  调用方重新 poll → 泵继续 await 设备。✅ 这正是 `pump_async()` 的形态。
- 如果**没有任何任务持有并 poll 这个泵循环**，waker 存下来也无人可唤——唤醒一个
  不存在的任务。这就是当前混合模式的处境：`park_producer`/`park_consumer`
  (core_.rs:715/753) 只被全主动 `Pipeline` 调用(spsc_.rs:636/638)，混合模式
  `DevProducer` 里根本没有「正在被 poll 的泵 future」可言。

一句话：**waker 是「叫醒服务」，不是「执行者」。** 缺的不是 waker，而是 poller。

### 7.2 那让 waker 自己回头 poll，行不行？

技术上「可以」，即所谓 self-waking future：waker 闭包里持有指向被 pin 住的泵
future 的指针，被调用时直接 `Future::poll` 它。但代价很高，四类问题：

1. **重入与死锁**：waker 可能在 reactor 线程、或在持有环状态（`advance_write` /
   `advance_read` 的提交路径）时被调用；此时回头 poll 泵会重入同一把锁 / 同一
   状态机 → 死锁或状态破坏。环状态与设备 IO 必须能并发推进才安全。
2. **在 reactor 线程上跑用户逻辑**：泵的下一步会再次 await 设备，即向同一个
   reactor 注册；在 reactor 的 waker 回调里做这件事属于自我重入，各运行时的
   保证不同，可能卡住 reactor。
3. **无界递归 / 栈增长**：设备若一直就绪，poll 完成 → fire 对端 → 又唤醒 → 再
   poll，递归深度随数据量增长；必须靠人工限流（这正是「搬一批就交还」R2 想解决的
   问题的另一面）。
4. **自引用 + `unsafe` + `Send`**：泵 future 必须固定在稳定地址、waker 存裸指针，
   且环核要求 `Send + Sync`(abs_comp_.rs:58)，跨线程唤醒时指针有效性靠约定而非
   类型保证。等于在环内部手搓一个微型 executor。

### 7.3 buffex 为什么不该自己 spawn

最省事的「自驱动」是构建期 `spawn` 一个泵任务，但 `buffex` 是 `no_std` 且
**运行时无关**：它不能假设存在 executor，也不能把 socket 塞进任务（compio socket
还 `!Send`）。因此「谁来 poll 泵」这件事**必须**留给调用方——这就是方案 A 让
`pump_async()` 公开、由调用方 join/spawn 的根本原因，也是方案 C 把「被动环 +
调用方泵」定为 socket 官方用法的原因。

### 7.4 与现有设计的关系

现有设计并非「不知道 waker 怎么用」，而是**把 poller 的职责presupose 成了对端的
提交操作**：`advance_read`/`advance_write`/`try_*`/`close` 驱动对端泵，每次只做一次
非阻塞 poll。这对**永远就绪的设备**是自洽且零开销的（现有 `pump_.rs` 测试正是
这种设备），但对会 `Pending` 的网络设备就缺少了「设备就绪 → 唤醒 poller」这条边。
方案 A 补的就是这条边：`pump_async()` 同时等待两个唤醒源——设备就绪（真 waker）与
环空/满（主动端 `WakeSlot`）。

## 8. 追问二：能否用 `abs_art-bridge` 提供 `spawn`，让主动端自驱动？

**结论：技术上成立，而且正好补上 §7.1 缺失的那一环（poller）；但推荐把它做在
「知道运行时的适配层」，而不是把 runtime 依赖塞进 `buffex` 内核。**

### 8.1 为什么它能成立

§7.1 的症结是「没有执行体持有并 poll 泵 future」。`spawn` / `spawn_local`
**就是**那个执行体：任务由运行时持有并轮询，设备 future 注册的 waker 唤醒的是
**真实任务**，于是「设备就绪 → 重新 poll 泵」这条边被补上。§7.2 里那些重入/死锁
风险也随之消失——重新 poll 发生在执行器里，而不是 waker 回调里。

工作区里 `abs_art` 是 `#![no_std]` 的能力位抽象
（`BLOCK_ON/DELAY/SPAWN_SEND/SPAWN_LOCAL/SPAWN_BLOCKING/FULL` +
`TrAsyncRuntime/TrSpawnSend/TrSpawnLocal/TrJoinHandle`，见
`abs_art/abs_art/src/{caps.rs,runtime.rs}`），`abs_art-bridge` 已经同时提供
**tokio（默认）/ compio / smol** 三个后端（`abs_art/abs_art-bridge/Cargo.toml`），
所以「同时适配 tokio 与 compio」在运行时抽象这一层是现成的。

### 8.2 `!Send` 的 compio socket 不是障碍——但要选对 spawn

- compio socket `!Send`（`SharedFd` 内含 `Rc`）→ 必须走 `spawn_local`
  （`TrSpawnLocal`，不要求 `Send`），且任务与 socket 留在同一线程。
- 注意 smol 的语义差异（`abs_art/src/runtime.rs:55-57`）：smol 的 `spawn_local`
  任务由**句柄**驱动，句柄不 poll 任务就不跑，`detach` 只对全局 `spawn` 任务有效。
  因此自驱动泵必须把 join handle 交给调用方保管，不能静默 detach。
- **关键点：设备根本不需要进环核。** 让 spawn 出来的泵任务持有
  `SockInput`/`SockOutput` 设备 + 环的 `Send+Sync` 半部即可（这正是
  `smux_v1/tests/common/mod.rs` 的拓扑，只是搬进任务）。于是
  `TrCircBuffCore: Send+Sync`(abs_comp_.rs:58) **不必放宽**——被放宽的是
  「buffex 不 spawn」这条契约，而不是 `Send + Sync` 约束。

### 8.3 代价与必须在设计里解决的三件事

1. **运行时耦合**：`abs_art-bridge` 的规则是「必须且只能启用一个后端」。一旦
   `buffex` 依赖它，**所有** buffex 使用方都被迫选后端；这与 buffex 现在
   「`no_std` + 运行时无关 + 零 spawn」的定位冲突。故推荐做成
   **可选 feature**（默认关闭）或独立适配 crate（如 `buffex-bridge` /
   放进 `abs_buff_tokio_adapt`、`abs_buff_compio_adapt`），内核保持纯算法。
2. **任务生命周期与取消**：自驱动泵一旦 spawn 就必须能被**停止**——环关闭 /
   连接断开 / 设备出错时任务要退出，否则永久 park 在死 socket 上（泄漏）。
   需要把 join handle 暴露给调用方（`abort`/`await`），并把「环关闭」事件接进
   泵的等待集合（主动端 `WakeSlot` 已有 `ConsumerClose`/`ProducerClose` 事件）。
3. **设备错误传播**（buffex 已列为待办）：当前泵把设备错误当作「本轮无数据」。
   spawn 之后错误必须跨 hook 通知被动端（否则被动端会一直等一个已经死掉的设备）。

### 8.4 与方案 A/C 的关系

- 方案 A（公开 `pump_async()`，调用方 join/spawn）与本节并不冲突：**A 是「谁
  spawn」交给调用方**；本节是**由库自己 spawn**。前者零运行时耦合、零新依赖，
  是默认推荐；后者更省心，但把运行时选择带进依赖链。
- 二者可以并存：内核提供 `pump_async()`，适配层（或 `abs_art` 能力位泛型）在其上
  提供 `spawn` 版本，调用方按需选择。
- 三者都不改变 §4 的结论：**socket 的默认用法仍是「全被动环 + 泵」**，区别只是
  泵由谁驱动、在哪个任务里跑。

## 9. 追问三：泵该按 socket 特化，还是按 trait 泛化？

**结论：按 trait 泛化；只保留两处「薄特化」——运行时绑定与 `Send`/`!Send` 选择。
不要按 socket 类型特化。**

### 9.1 为什么不按 socket 特化

泵真正依赖的只有三件事：**字节设备**、**环的被动半部**、**某个 spawn 能力**。
「是不是 socket」与它无关。若按类型特化，就要为 `UnixStream` / `TcpStream` /
`DuplexStream` / `TlsStream` / compio 的各种 fd 各写一遍，还排除了用户自定义设备。
这正是「不是所有 `AsyncRead`/`Write` 都需要 spawn」的反面：需要的是**能力**，不是
**类型**。

### 9.2 泛化的三个维度（都用 trait，而不是具体类型）

| 维度 | 抽象 | 说明 |
| --- | --- | --- |
| 设备 | `abs_buff::io::{TrInput, TrOutput}` | 已经是运行时无关的字节设备契约；tokio/compio 适配器都实现它 |
| 环半部 | `abs_buff::{TrBuffWrite, TrBuffRead}` | 不绑 `buffex` 具体类型，任何环形实现都能用 |
| 执行体 | `abs_art::{TrSpawnSend, TrSpawnLocal}` + `TrJoinHandle` | `abs_art` 是 `no_std` 能力位抽象，tokio/compio/smol 后端齐备 |

三者的组合就是泵的全部依赖，因此泵本身可以只依赖 `abs_buff` + `abs_art`
（`buffex` 只在调用方作为环实现出现）。

### 9.3 保留的两处薄特化

1. **运行时绑定**：每个适配 crate 只需一个类型别名/一行绑定，把泛型泵固定到自己的
   运行时，例如 `abs_buff_tokio_adapt::pump::TokioPump`、
   `abs_buff_compio_adapt::pump::CompioPump`。这是编译期零成本、零重复的特化，
   正是「放进两个适配 crate」的落点。
2. **`Send` / `!Send` 两条构造**：由 `abs_art` 的能力位在**类型层**区分——
   `spawn_send()`（要求 `Device: Send + 'static`，tokio 用）与 `spawn_local()`
   （不要求 `Send`，compio 用）。运行时缺哪个能力，对应方法就不存在，编译期即拒绝。

### 9.4 适配器本身保持「纯包装、不 spawn」

`ReadAsInput` / `WriteAsOutput` / `CompioReadAsBuff` / `CompioWriteAsBuff` **不**引入
spawn：它们只是设备包装。泵是**独立的、opt-in 的组合子**。这样：

- 不需要 spawn 的用途（永远就绪设备、由调用方 join 的场景）零额外代价、零运行时耦合；
- 需要 spawn 的用途显式构造泵，并拿到 `JoinHandle` 以便 abort/await。

### 9.5 无论是否泛化都必须做好的两件事

- **停止/关闭传播**：环关闭、连接断开、对端 `close` 事件要接进泵的等待集合，
  否则任务永久 park（主动端 `WakeSlot` 已有 `ConsumerClose`/`ProducerClose` 可复用）。
- **设备错误传播**：错误必须跨 hook 通知被动端（buffex 现有待办），否则被动端会一直
  等一个已死的设备。

## 10. 追问四：拆成 `buffex_pump_tokio` / `buffex_pump_compio` 两个 crate（人类方案确认）

**方案**：新增两个 crate，分别适配 tokio 与 compio 的 spawn 策略；**不依赖
`abs_art-bridge`**；**不新增抽象 trait**，统一建立在使用现有 `TrInput` / `TrOutput`
之上。

**结论：方向正确，是对 §9 的合理落地。** 它用「按运行时拆 crate」换掉了「引入
`abs_art` 能力位 + 薄别名」这一层，好处是**不与后端选择耦合**（避免
`abs_art-bridge` 的「必须且只能启用一个后端」传染），并可直接用各运行时的原生
spawn 与其原生错误/取消语义。三点需要明确：

1. **泵的签名建议落在 `abs_buff` 的 trait 上，而不是 `buffex` 的具体类型**：
   设备用 `TrInput` / `TrOutput`，环半部用 `TrBuffWrite` / `TrBuffRead`。这样两个
   pump crate 只依赖 `abs_buff` + 各自运行时；`buffex` 只在调用方作为环实现出现。
   （crate 名沿用 `buffex_pump_*` 没问题，但依赖面可以更窄。）
2. **`spawn` / `spawn_local` 必须按运行时如实选择**：tokio 的 `spawn` 要求
   `Send + 'static`；compio 的 socket 是 `!Send`，因此 compio 侧要么存在可用的
   local spawn，要么该 crate 只能返回**调用方驱动的 future**（即退回方案 A）。
   **这一点需以实现时的 compio 运行时 API 为准核对**，不要假设两个 crate 的 API
   形状完全相同。
3. **没有公共 trait ⇒ 泵循环会在两个 crate 里各写一份**。若循环体很小（读设备→写环、
   读环→写设备 + 关闭/错误处理）可以接受；若变大，可抽**私有**共享实现（不对外暴露
   trait），或用宏生成。这是一次有意识的取舍，不要让两份实现悄悄漂移。

**两个 crate 无论怎么做都必须处理**（与 §8.3/§9.5 相同）：
- **停止/关闭传播**：环关闭、对端 close、连接断开要能让泵任务退出，句柄可
  abort/await，避免永久 park；
- **设备错误传播**：错误要跨 hook 通知被动端（buffex 现有待办），否则被动端会一直
  等一个已死的设备；
- **句柄所有权**：把 `JoinHandle` 交给调用方（尤其 smol 语义下必须保住句柄），
  不静默 detach。
