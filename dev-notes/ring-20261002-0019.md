# 环形缓冲的关闭入口：`close_producer` / `close_consumer` 与 EOF 例外

日期：2026-10-02 00:19
涉及：`src/ring/ring_core_.rs`（主体）、`src/ring/half_.rs`、`src/ring/tests_.rs`
动机：`buffex_compio_adapt` 的后台泵需要「设备结束 / 收尾」能唤醒在对端 park 的等待者

## 1. 问题：状态字早就有「已关闭」，却没有任何入口置位

`RingState` 里一直有 `PRODUCER_CLOSED` / `CONSUMER_CLOSED` 两个标志，
`try_read_internal_` / `try_write_internal_` 也已经按它们返回 `Closing`
（`ring_core_.rs` 的各分支），`is_producer_closed` / `is_consumer_closed` 也是公开的——
但**没有任何代码把它们置起来**，也没有任何路径会在置位后唤醒对端。后果（在适配器侧就是
挂死）：

* 设备读到 EOF 时，消费者正 park 在 `read_async` 上：不会再有 `advance_write`，没人唤醒它；
* 收尾时想让泵「排空后收工」：泵 park 在空环上，没有任何信号能叫醒它。

绕过办法（在适配器里自造「通知 + select 竞速」）要两个方向各写一套，还得自己合成
`Drained → Closing`——而 ring 的状态语义天生就是干这个的。

## 2. 改动

### 2.1 新增关闭入口

```rust
Ring::close_producer(&self)   // 幂等：置 PRODUCER_CLOSED，唤醒等待中的消费者
Ring::close_consumer(&self)   // 幂等：置 CONSUMER_CLOSED，唤醒等待中的生产者
RingWriter::close(&self)      // = close_producer
RingReader::close(&self)      // = close_consumer
```

* 收 `&self`：只动状态字、不碰数据区，因此「读半部宣告自己不再消费」不需要 `&mut`；
* 幂等由 CAS 仲裁：只有抢到「置位」的一方负责唤醒（`try_set_*_closed_`）；
* 唤醒复用既有协议（与 `advance_write` / `advance_read` 同款）：先看兴趣位快照，
  再让 `Consumer::wake` / `Producer::wake` 在锁内做「判定 → 认领 → 取走」，唤醒放在锁外。

### 2.2 判定面与唤醒谓词必须同步改（否则漏唤醒）

关闭意味着条件**永久**不可能再被满足，因此等待者必须被唤醒去拿 `Closing`：

| 位置 | 改动 |
| --- | --- |
| `RingState::can_consume_` | `data_size() >= min \|\| is_producer_closed()` |
| `RingState::can_produce_` | `free_size() >= min \|\| is_consumer_closed()` |
| `Consumer::wake` 的判定闭包 | 同上（与 `can_consume_` 保持一致） |
| `Producer::wake` 的判定闭包 | 同上 |

两处必须一致：`try_register_`（等待者复检）用 `can_*`，对端唤醒用 `wake` 的闭包；
只改一处会出现「登记后睡死」或「永远不唤醒」。

### 2.3 顺带修掉 `try_read_internal_` 未兑现的 EOF 例外

该函数的文档早就写明「**EOF 例外**——写端已关闭时返回现有部分（可能不足下限）」，但
代码没有兑现。补上 `close` 之后这会变成**忙等**：等待者以 `at_least(k)`（k>1）park →
`close_producer` 唤醒（`can_consume_` 现在为真）→ `try_read_` 仍返回 `Drained` → 再 park
→ 立刻又醒……一圈不 await 的紧循环。修法：

```rust
if ready < min_len {
    if !has_flag(s, PRODUCER_CLOSED) {
        return Err(ConsumerError::Drained(pos.rp));
    }
    // 已关闭：交付现有部分（EOF 例外）
}
```

对既有调用方无影响：`k == 1` 时 `ready < 1` 等价于 `ready == 0`，本来就走「空环 + 已关 →
`Closing`」分支（`buffex_tokio_adapt` 的所有调用方都是 `at_least(1)`）。

## 3. 关闭之后的语义

| 操作 | 已关生产端 | 已关消费端 |
| --- | --- | --- |
| `try_read` / `read_async` | 有数据照常给（可不足下限）；取空 → `ConsumerError::Closing` | `ConsumerError::Closing` |
| `try_write` / `write_async` | `ProducerError::Closing` | `ProducerError::Closing` |
| park 中的等待者 | 立即被唤醒并拿到 `Closing` | 同 |
| `is_producer_closed` / `is_consumer_closed` | `true` | `true` |

## 5. 遗留

* 关闭是**单向**的：`close_producer` 之后不能再「重新打开」。若将来需要半关闭重开，
  得另加 `reset` 语义（目前没有需求）。
* `buffex_tokio_adapt` 仍自带一层 `Drained → Closing` 合成；它可以借这次新增的 `close`
  退化成直接转发，但那属于另一个 crate 的改动，本轮不动。
* 适配器侧的「原始预留 + 外部提交」（零拷贝窗口）是另一条线，见
  `buffex_compio_adapt/dev-notes/` 的相关记录，本轮不涉及。
